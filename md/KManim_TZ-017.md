## 1. Обзор проекта

### 1.1. Что такое Manim (краткий ликбез для контекста)

Manim — это Python-движок для создания точных математических анимаций программным способом, получивший известность благодаря образовательным видео канала 3Blue1Brown. В Manim разработчик описывает **сцену** классом с методом построения, внутри которого создаёт **математические объекты** (mobjects) — окружности, линии, формулы, оси координат — и проигрывает над ними **анимации** (появление, перемещение, превращение). Классический Manim покадрово вычисляет состояние объектов, рисует каждый кадр и склеивает кадры в видеофайл через FFmpeg. Это пакетный процесс без интерактивности; его результат — `.mp4`.

### 1.2. Что строим мы

**KManim — нативная Android-библиотека на Kotlin, воспроизводящая концепции и выразительность Manim, но работающая в реальном времени на устройстве, без видеоэкспорта как основного режима и без каких-либо зависимостей от Python.**

Ключевое концептуальное отличие от оригинала: Manim рендерит кадры на диск и собирает видео; KManim выполняет ту же покадровую модель (вычислить состояние объектов в момент времени → нарисовать кадр), но **в реальном времени на экране Android с частотой 60 кадров в секунду**. Видео как промежуточный артефакт исчезает; взамен появляется интерактивность.

### 1.3. Цели

1. Достичь существенного паритета с Manim по выразительным средствам (объекты + анимации + DSL).
2. Рендеринг в реальном времени, целевая частота — **60 FPS**.
3. **Чистый Kotlin**, опора на нативные Android API и JVM-библиотеки. Никакого Python и никаких гибридных схем (см. раздел 4.1).
4. **Идиоматичный Kotlin-DSL** для описания сцен и анимаций (см. раздел 5.6).
5. **Модульная архитектура**, пригодная для расширения сообществом (см. раздел 6).
6. **Абстракция рендерера**, открывающая путь к 3D, Vulkan, Filament, Android XR / OpenXR без переписывания ядра (см. раздел 5.5 и 11).
7. **Создание статического веб-зеркала документации (`docs/`)**, выступающего в роли первоклассного исполняемого артефакта и спецификации паритета (см. раздел 10.1).

### 1.4. Не-цели (что мы сознательно НЕ делаем)

- **Не** реализуем запись или экспорт кадров/видео — это сознательно вне области проекта. Архитектура оставляет точку расширения, чтобы такую возможность мог добавить сторонний плагин/модуль, если этого захочет сообщество (см. 11.4); сами мы её не ведём.
- **Не** портируем Python-код Manim построчно — это невозможно (раздел 4.1).
- **Не** стремимся к 100% паритету с Manim *как продуктом* — это недостижимо чистым Kotlin (раздел 1.5). Стремимся к 100% покрытия сценариев, которые реально хотим анимировать.
- **Не** тащим тяжёлые низкоуровневые решения раньше времени: сырой Vulkan не пишется на старте (раздел 4.4, 9 — Спринт 7).

### 1.5. Определение успеха

Метрика успеха переформулирована осознанно. Чистым Kotlin реалистично достижимо **~70–80% функциональности Manim** (ограничения — в разделе 11.5). Однако цель проекта измеряется не этим числом, а другим:

> **Успех = 100% покрытия сценариев анимации, которые мы реально хотим создавать, при стабильных 60 FPS и при сохранении чистоты архитектуры.**

Прогресс к этой цели отслеживается **Журналом паритета API** (`API_PARITY.md`, раздел 10), который показывает, какая часть API Manim реализована, частично реализована, не реализована или принципиально не портируема.

### 1.6. Целевая платформа

- **Платформа:** Android (нативное приложение/библиотека).
- **Язык:** Kotlin.
- **Рендеринг 2D:** Android Canvas API (под капотом — Skia, аппаратное ускорение через HWUI).
- **Рендеринг 3D (позже):** через абстракцию `Renderer3D`; бэкенд — **Filament** (зафиксирован, D-28; см. разделы 7, 11).
- **Минимальная версия Android:** Android 14 (API 34).
- **Целевые устройства:** любые, без ограничений по производителю или классу устройства.

## 2. Образец для подражания: какую версию Manim берём за основу

Существуют две основные кодовые базы Manim, выросшие из общего корня (ManimCE — форк репозитория Гранта Сандерсона):

| | **ManimCommunity / manim (ManimCE)** | **3b1b / manim (ManimGL)** |
|---|---|---|
| Кто ведёт | Сообщество | Грант Сандерсон лично |
| Назначение | Стабильная общедоступная библиотека | Инструмент для собственных видео автора |
| Рендеринг 2D | Cairo (immediate-mode рисование путей) | OpenGL / moderngl (GPU) |
| API | Стабильный, документированный, семантическое версионирование | Экспериментальный; ломающие изменения между версиями **не документируются** |
| Экосистема | Тесты, CI, система плагинов, активное комьюнити | Менее формализована |
| Пакет PyPI | `manim` | `manimgl` |

**Решение по образцу:**

- **API и иерархию объектов зеркалим с ManimCE.** Причины: стабильный задокументированный API даёт чёткую спецификацию (а не движущуюся мишень); у ManimCE уже есть модульная/плагинная философия, которую мы хотим воспроизвести для сообщества; его Cairo-рендеринг концептуально близок к immediate-mode Android Canvas (рисование путей).
- **3b1b/manim держим как референс для 3D и GPU-рендеринга.** Его подход на OpenGL/moderngl и шейдерах — более близкий образец для нашего будущего 3D-бэкенда, чем Cairo-рендеринг ManimCE.

Итого: **API и библиотека объектов — по ManimCE; архитектура 3D-рендера — с оглядкой на 3b1b.**

## 3. Глоссарий

| Термин | Определение |
|--------|-------------|
| **MObject** | Базовый класс любого объекта сцены (от Manim *Mobject* — mathematical object). Хранит трансформацию, дочерние объекты, стиль; не содержит кода, привязанного к конкретному бэкенду рендеринга. |
| **VMobject** | Векторный MObject (от *Vectorized Mobject*). Хранит геометрию как последовательность **кубических кривых Безье**. Окружности, многоугольники, текстовые глифы, графики — всё это VMobject. |
| **Submobjects** | Дочерние объекты внутри MObject; объект — это дерево. Трансформации и анимации распространяются по дереву. |
| **VGroup** | `MObject` без собственной геометрии (`draw` пуст), служащий контейнером для группового перемещения/масштаба/поворота и распространения анимаций; его дети — это `submobjects` базового `MObject` (VGroup не дублирует дерево, а является именованным типом контейнера над ним). См. 5.2, Приложение A, D-39. |
| **Animation** | Объект, описывающий изменение MObject во времени. Имеет длительность (`rateFunc: RateFunction`) и приводит цель в состояние, соответствующее `alpha`. Контракт раздвоен (D-35): базовый `interpolate(alpha)` мутирует целевой `MObject` (матрица/прозрачность/значения); контуро-порождающие анимации дополнительно реализуют `interpolatePath(alpha, out: FlatVectorPath)` (zero-alloc). |
| **alpha** | Нормализованное время анимации в диапазоне `[0.0, 1.0]`: 0 — начало, 1 — конец. |
| **Rate-функция (easing)** | Функция `(alpha: Float) -> Float`, искривляющая ход времени для естественности движения (например `smooth`, `linear`, `there_and_back`). |
| **Scene** | Контейнер, управляющий списком MObject и проигрыванием анимаций; владеет тактовым циклом рендеринга. |
| **RenderContext** | Backend-нейтральный интерфейс, через который объекты рисуют себя. Даёт доступ к `Renderer2D` и `Renderer3D`, но скрывает, какой бэкенд под ними. |
| **Renderer2D / Renderer3D** | Интерфейсы-«порты» рендеринга. Говорят на языке примитивов (`fillPath`, `drawMesh`), а не фигур. Реализуются конкретными бэкендами. |
| **Бэкенд (backend)** | Конкретная реализация рендерера: `CanvasRenderer2D`, `GLES3Renderer3D`, `FilamentRenderer3D` и т.д. |
| **Шов (seam)** | Граница абстракции — место, где код ядра перестаёт знать о деталях реализации. В KManim шов проходит на уровне примитивов отрисовки. |
| **Opaque handle (непрозрачный хэндл)** | Ссылка на GPU-ресурс (например `MeshHandle`), за которой стоит реальный буфер, которым владеет бэкенд. Объекты держат хэндл, но никогда — сырой id ресурса. |
| **Golden-image тест** | Тест, рисующий кадр в `Bitmap` и сравнивающий его с эталонным PNG с допуском на сглаживание. |
| **DSL** | Domain-Specific Language — предметно-ориентированный синтаксис описания сцен, построенный средствами Kotlin (lambda-with-receiver, extension-функции, перегрузка операторов, infix-функции). |
| **NDC** | Normalized Device Coordinates — нормализованные координаты устройства после проекции. Различаются у графических API (см. раздел 5.5.4). |
| **VectorPath** | Собирательный (прозовый) термин для 2D-геометрии-как-путей. **Не является самостоятельным классом/типом в коде.** В коде существует ровно в двух нормативных представлениях — `TopologicalPath` (объектная модель, холодный путь) и `FlatVectorPath` (плоский `FloatArray`, горячий путь), см. 5.2.1 и D-34. В сигнатурах, конструкторах и тестах всегда используется конкретное из двух представлений, а слово «VectorPath» допустимо только в прозе как обобщение. |
| **TexEngine** | Внутренний интерфейс движка формул: `(String) -> TopologicalPath`. Скрывает конкретную реализацию (KaTeX) за швом, делая её заменяемой. См. разделы 5.8, 5.2.1. |
| **SceneFrame / Camera2D** | Логическая 2D-камера ядра: видимое окно сцены в manim-юнитах (`frameWidth`/`frameHeight`/`center`); по умолчанию 14.222×8.0 юнита при 16:9. Задаёт преобразование сцена→экран (вьюпорт-`Mat3`). Отдельна от `Camera` (та — только 3D-матрицы `Mat4`). См. 5.5.6, D-38. |
| **InputEvent** | Доменное событие ввода (нормализованные координаты сцены + фаза down/move/up), которым UI-поток наполняет неблокирующую очередь; разбор и hit-testing — на `RenderThread` в начале кадра. См. 5.10, D-44. |
| **Dirty-флаг** | Логический маркер, указывающий, что состояние объекта (например, форма контура) изменилось и требует пересчёта. Позволяет кэшировать тяжелые вычисления. |
| **Zero-allocation** | Подход к написанию кода, при котором в критических секциях (например, в цикле рендеринга) не происходит выделения новой памяти, чтобы избежать пауз сборщика мусора (GC). |
| **VSYNC** | (Vertical Synchronization) Аппаратный сигнал обновления экрана. В KManim цикл отрисовки синхронизируется с VSYNC, чтобы избежать разрывов кадров (tearing) и микрофризов. |

## 4. Принципы и ключевые архитектурные решения

Каждое решение приведено вместе с обоснованием, чтобы читатель понимал не только «что», но и «почему».

### 4.1. Чистый Kotlin, без Python

Прямой порт Manim невозможен: библиотека опирается на Python-специфичные зависимости (NumPy для вычислений, Cairo для 2D-рендеринга, FFmpeg для видео, пайплайн LaTeX → dvi → SVG для формул). Гибридные схемы (встраивание Python) отвергаются сознательно. Вместо порта — **переосмысление концепций Manim средствами Android и JVM**.

### 4.2. Рендеринг в реальном времени вместо видео

Покадровая модель Manim сохраняется, но кадры идут на экран в реальном времени, а не на диск. Это не только проще (исчезает шаг FFmpeg), но и даёт интерактивность как преимущество перед оригиналом.

### 4.3. Модульность ради расширяемости сообществом

Ядро держим тонким, объекты раскидываем по модулям с чёткими интерфейсами. На Android это естественно ложится на Gradle-модули (раздел 6). Цель — чтобы стороннему контрибьютору можно было добавлять объекты, не трогая движок. Это прямое воспроизведение модели развития ManimCE.

### 4.4. Абстракция рендерера закладывается сразу, реализуется поэтапно

**Решение:** интерфейсы рендеринга (`RenderContext`, `Renderer2D`, `Renderer3D`) проектируются и вводятся в код **с самого начала**; но второй (3D) бэкенд **реализуется только после того, как 2D-ядро полностью готово** (Спринт 7).

**Обоснование:** заложить интерфейс рано — дёшево; ретрофитить абстракцию в код, который везде напрямую дёргает конкретный графический API, — крайне дорого. При этом реализовывать тяжёлый бэкенд (сырой Vulkan) раньше времени — преждевременная оптимизация. Решение разделяет эти два момента.

**Гарантия:** при правильно поставленном шве (раздел 5.5) переход с одного бэкенда на другой не затрагивает ни DSL, ни иерархию объектов, ни анимации. Это и есть условие для будущих Android XR / OpenXR / Vulkan / Filament.

### 4.5. Шов проходит на уровне примитивов, а не фигур

Интерфейс рендерера обязан говорить `fillPath()` / `drawMesh()`, а **не** `drawCircle()`. Иначе каждый бэкенд переписывал бы логику фигур заново. Геометрия объекта (как окружность превращается в кривые Безье) — общий код внутри объекта; растеризация этих кривых — за интерфейсом. Это инвариант архитектуры, нарушать его нельзя.

### 4.6. Выбор бэкенда — по типу сцены, а не глобально

2D и 3D в Manim смешиваются в одной сцене (например, 3D-оси с плоскими 2D-подписями). Гибрид «Canvas для 2D + GPU для 3D» неудобен для смешанных кадров: компоновка потребовала бы рендера 3D в офскрин-фреймбуфер, выгрузки как текстуры и наложения в Canvas — лишний roundtrip и отсутствие корректного перекрытия 2D объёмом.

**Решение:** бэкенд выбирается по типу сцены. Обычная 2D-сцена идёт целиком через Canvas/Skia. `ThreeDScene` идёт целиком через GPU-бэкенд, и 2D-оверлеи внутри неё рисуются тем же GPU-векторным рендером. Тогда внутри одного кадра всегда один пайплайн, и компоновка естественна. (Для сравнения: ManimGL пошёл по пути «вообще всё — это 3D», Canvas там нет совсем; мы сохраняем Canvas для 2D ради качества и простоты.)

### 4.7. Переиспользуем готовые Android-API за интерфейсом, где это не вредит паритету

Где Android уже даёт нужную функциональность, мы оборачиваем её за нашим интерфейсом, а не переписываем с нуля. Это прямое продолжение инварианта 4.5 и уже применяется: 2D-растеризация — Canvas/Skia, вёрстка текста — `StaticLayout`, матрицы — `android.graphics.Matrix`. Так же можно поступать с чем угодно ещё: например, `android.view.animation.Interpolator` (и его AndroidX-родня) — это по сути та же `(Float) -> Float`, что и наш `rateFunc`, поэтому любой системный интерполятор адаптируется к нашему `RateFunction` в одну строку.

**Важная оговорка про паритет.** Этот принцип подчинён принципу зеркалирования API ManimCE (D-3). Там, где требуется бит-в-бит совпадение с поведением Manim — а это весь каталог rate-функций (D-14) — мы реализуем именно математику Manim, а не подменяем её похожим, но другим системным интерполятором (например, `BounceInterpolator` ≠ манимовский `ease_out_bounce`). Системные интерполяторы при этом можно предлагать как *дополнительные* варианты сверх манимовского набора через тот же интерфейс `RateFunction`. Иными словами: «не изобретать велосипед» действует везде, кроме случаев, где точный паритет требует именно манимовской кривой.

### 4.8. Рассмотренные и отклонённые альтернативы

Чтобы не возвращаться к одним и тем же развилкам, фиксируем крупные отклонённые варианты с причиной:

| Альтернатива | Почему отклонена |
|--------------|------------------|
| **Мультиплатформа на Kotlin Multiplatform + Skiko** | Skiko (Skia для KMP) переносит только растеризацию путей, но **не** Android-специфику в сердце проекта: `SurfaceView`/`lockHardwareCanvas` (D-22), `AHardwareBuffer` (D-18), `Choreographer`/VSYNC, биндинги Filament. Мультиплатформа = заново решать потоки, поверхности, синхронизацию и 3D на каждой платформе. Это та сложность, ради ухода от которой выбран фокус на Android (D-1). |
| **KManim поверх Jetpack Compose (как движок)** | Compose реактивен и про «состояние сейчас»; рекомпозиция скрывает ось времени. Нам нужна явная ось времени и точный контроль `alpha` для покадровой математической анимации (раздел 5.6). Сходство синтаксиса DSL — приветствуется, исполнение — своё. |
| **Сырой Vulkan для 3D на старте** | Даёт доступ к GPU, но не даёт векторную графику; «нарисовать треугольник» — сотни строк инфраструктуры. Filament закрывает сложность и сам ведёт к Vulkan через `Renderer3D` (раздел 7). |
| **Полноценный веб-рендеринг (Kotlin/Wasm)** | Наш рендер — нативные Android Canvas/Filament; в браузере их нет. Веб потребовал бы отдельной реализации `Renderer2D` под Skiko/Canvas-web и не покрыл бы 3D. Несовместимо с фокусом D-1 как часть ядра — но достижимо как плагин на краю (см. ниже и D-26). |
| **JLaTeXMath для формул** | Намертво завязан на отсутствующий в Android `java.awt`; форк по объёму сравним со всем движком. Заменён на KaTeX→SVG→`VectorPath` (D-20). |

**Переносимость через шов (D-25).** Отказ от мультиплатформы — не тупик. Благодаря шву (раздел 5.5: `RenderContext` → `Renderer2D`/`Renderer3D`, `TexEngine`) код делится на переносимое ядро (DSL, объекты, анимации, геометрия, тайминг — чистый Kotlin без Android) и платформенные адаптеры (рендереры, поверхность, потоковая модель). Поэтому будущий **порт на десктоп/веб/иную платформу — это «реализовать интерфейсы заново», а не «переписать движок»**: переезжает большая часть кода, переписываются только адаптеры под новое железо. Веб-рендеринг (Skiko/Canvas-web под Wasm) и иные таргеты подключаются именно так — как новые реализации существующих портов, не трогая ядро (D-26), ровно как Vulkan/XR. Это работает ровно настолько, насколько герметичен шов: инвариант 5.1 («ядро никогда не знает про бэкенд») — это в том числе страховка переносимости.

### 4.9. Стандарты написания кода и структура проекта

Для поддержания высокого качества кодовой базы, читаемости и инкапсуляции, зафиксированы следующие правила (добавлено перед стартом Спринта 0):
1. **Интерфейс + Имплементация только для архитектурных швов:** Строгое разделение применяется только к системным сервисам и движкам (например, `Renderer2D`, `TexEngine`, `RateFunction`). Это обеспечивает полиморфизм и слабую связность.
2. **Фигуры и Анимации — это классы:** Доменные объекты (`Circle`, `Transform`, `MObject`) реализуются как обычные `open` или `abstract` классы. Детали реализации и внутреннее состояние скрываются за модификаторами `internal` и `private`. Инстанцирование происходит через функции DSL (`fun circle(...)`).
3. **Исключение для горячего пути (Zero-Allocation, решение D-36):** Источник аллокационной чистоты в кадровом цикле — **не** value-семантика, а (а) плоское хранение координат в `FloatArray` (`FlatVectorPath`, D-23) и (б) пулы/предвыделенные mutable-объекты с записью в `out`-параметр. Конкретно: `Vector2`, `Matrix`/`Mat3`/`Mat4`, `Transform` — **обычные mutable дата-классы без интерфейсов**, переиспользуемые через пул и/или `out`-параметр (мутация предвыделенного экземпляра), а **не** `value class` (мультиполевой `@JvmInline value class` нестабилен на Kotlin 2.0). Единственный кандидат в `@JvmInline value class` — однополевой `Color` (упакованный ARGB `Int`); **оговорка:** даже однополевой value class боксится как тип-аргумент дженерика, как nullable (`Color?`) и при хранении в коллекции, поэтому в горячем пути его не кладут в `List`/контейнеры. (Согласовано с Приложением A, где ни один тип не помечен `value class`.)
4. **Один класс — один файл:** Файлы должны быть небольшими и логически разделенными.
5. **Неймспейс пакетов:** Модули используют короткий префикс `kmanim.*` (например, `kmanim.core`, `kmanim.geometry`).
6. **Линтинг:** Использование статических анализаторов (detekt / ktlint) для контроля чистоты кода.
7. **Build-Logic и Version Catalog:** Общая логика сборки Gradle выносится в convention plugins через композитную сборку `includeBuild("build-logic")` (плагины `kmanim.android.library`, `kmanim.android.application`), а все версии и зависимости централизуются строго в `gradle/libs.versions.toml` (AGP 8.4+, Kotlin 2.0+), чтобы исключить дублирование и конфликты версий.

## 5. Архитектура системы

### 5.1. Слоистая структура

```
┌─────────────────────────────────────────────────────┐
│  DSL  (scene { ... play(...) ... })                   │  ← пользовательский код
├─────────────────────────────────────────────────────┤
│  Объекты (MObject / VMobject / Circle / Axes / ...)   │  ← backend-нейтральны
│  Анимации (Animation / Create / Transform / ...)      │
│  Scene + тактовый цикл рендеринга                     │
├─────────────────────────────────────────────────────┤
│  RenderContext  →  Renderer2D | Renderer3D            │  ← ШОВ (абстракция)
├─────────────────────────────────────────────────────┤
│  Бэкенды: CanvasRenderer2D | GLES3Renderer3D |        │  ← знают про железо
│           FilamentRenderer3D | (Vulkan, XR...) позже  │
└─────────────────────────────────────────────────────┘
```

**Инвариант:** всё, что выше шва (DSL, объекты, анимации, сцена), **никогда** не ссылается на конкретный бэкенд. Это проверяется в том числе тестом из Спринта 7 (2D-ядро не меняется ни на строку при добавлении 3D-бэкенда).

### 5.2. Иерархия объектов

- **`MObject`** — базовый класс. Поля: `transform` (положение/масштаб/поворот), `submobjects` (дети), стиль. Метод `draw(ctx: RenderContext)` — абстрактный; метод `render(ctx)` рекурсивно рисует себя и детей. **Не содержит** вызовов Canvas/GL.
- **`VMobject : MObject`** — векторный объект. Геометрия — последовательность кубических кривых Безье в **двухуровневом представлении** (решение D-23, см. 5.2.1): объектный `TopologicalPath` для холодных операций над формой и плоский `FlatVectorPath` (`FloatArray`) для горячей покадровой интерполяции. Это снимает противоречие «чистота кода математики ↔ скорость без нагрузки на GC». Большинство конкретных объектов наследуются отсюда.
- **Конкретные объекты** — вычисляют свою геометрию (путь Безье) один раз и в `draw` передают её в `ctx.r2d.fillPath(...)` / `strokePath(...)`. Примеры: `Circle`, `Square`, `Line`, `Polygon`, `Dot`, `Arc`, `Axes`, `NumberPlane`, `ParametricFunction`.
- **Текст — два разных класса (важно, решение D-19).** Растровый и контурный текст принципиально различаются по возможностям:
  - **`TextLabel`** — высокоуровневый текст через `StaticLayout`/`Paint.drawText`. Быстрый, поддерживает переносы, эмодзи, кастомные шрифты, системное сглаживание. Поддерживает анимации `FadeIn`/`FadeOut`/`Shift`/`Scale`, но **не** `Create` и **не** `Transform` в фигуру — у растрового текста нет векторного контура.
  - **`VectorText`** — контурный текст: при создании извлекает контуры глифов через `Paint.getTextPath(...)` в `VectorPath`. Это `VMobject`, поэтому поддерживает честный `Create` (прорисовка штрихом) и `Transform` (морфинг в другие фигуры). **Ограничение (зафиксировать в документации):** `getTextPath` выстраивает глифы по базовой линии и **не** обрабатывает кернинг, лигатуры и двунаправленный текст (RTL — арабский/иврит). Для математического движка это допустимое ограничение первого этапа. Берётся там, где нужна именно анимация контуров.

- **`VGroup : MObject` (решение D-39).** Тонкая группа поверх существующего дерева `submobjects`: **не имеет собственного контура** (`draw` пуст), трансформация группы применяется к матрице, наследуемой детьми через `render()`; добавление/удаление ребёнка ставит dirty-флаг агрегированных границ (5.9). VGroup **не дублирует** `submobjects`, а является именованным типом контейнера над ним. Матричный инвариант (трансформа группы домножается на трансформы детей при обходе дерева) — это «накопление матриц перехода», корректность которого проверяет jqwik-тест Спринта 2. Kotlin-сахар (`+=`, индексация, `arrange()`) живёт в `*Ext.kt` (15.1). Пер-дочернее смещение времени анимации (`lag_ratio` для `LaggedStartMap`) — точка расширения, детализируется при портировании соответствующего примера галереи, а не в Спринте 2.

Эталонный контракт классов — Приложение A.

### 5.2.1. Двухуровневая модель геометрии (TopologicalPath / FlatVectorPath)

По итогам третьего аудита `VectorPath` разделён на два представления (решение D-23 пересмотрено) — это снимает реальный риск Спринта 3: писать математику морфинга (сопоставление контуров, направление обхода, рост из центроидов) на сыром `FloatArray` крайне сложно и чревато off-by-one, а гонять покадровую интерполяцию на дереве объектов — значит жечь GC.

- **`TopologicalPath` (холодный путь, объектная модель).** Структура из подпутей `SubPath`, каждый — список сегментов `CubicBezier`. Используется для редких дорогих операций над *формой*: сопоставление точек контуров, подразбиение, реверс направления обхода, топологическая подготовка морфинга (Спринт 3, D-24). Код этих алгоритмов пишется на понятных объектах, а не на индексах массива.
- **`FlatVectorPath` (горячий путь, плоский `FloatArray`).** Получается быстрой «линеаризацией» `TopologicalPath`. Используется **только** в кадровом цикле — для интерполяции `alpha` и передачи в `Renderer2D`. Аллокационно-чист (раздел 5.9).

**Контракт перехода.** Компиляция `TopologicalPath → FlatVectorPath` (каноничное имя операции — `toFlat(): FlatVectorPath`, см. Приложение A, D-35) происходит **только при изменении формы** (сигнал — dirty-флаг из 5.9), редко. Поскольку это **холодный путь**, компиляция **может аллоцировать** новый `FlatVectorPath` — ограничение «писать в предвыделенный `out`-контейнер» (zero-alloc, 5.9 п.2) действует **только** для покадровой интерполяции, а не для редкой перекомпиляции формы. Покадровая интерполяция в горячем пути идёт строго **между двумя уже скомпилированными `FlatVectorPath`** (A→B); компиляция из топологии в горячем пути **запрещена** — иначе двухуровневость не даёт выигрыша. Перемещение/масштаб/поворот меняют только матрицу и не требуют ни компиляции, ни перестроения пути.

### 5.3. Система анимаций

- **`Animation`** — базовый класс (контракт — Приложение A; решение D-35). Поля: целевой `MObject`; публичное `duration: Float` (секунды) — то, что задаёт DSL; rate-функция `rateFunc: RateFunction` (именованный `fun interface`, см. 4.9/Приложение D; SAM-совместим с `(Float) -> Float` и системными `Interpolator`, 4.7). **Каноничная внутренняя единица времени — наносекунды:** `Scene` один раз при старте анимации конвертирует `duration` в `durationNanos: Long` и считает `alpha` по наносекундной дельте кадра (Приложение B). **Метод `interpolate(alpha: Float)`** приводит объект в состояние, соответствующее нормализованному времени `alpha`, **мутируя сам `MObject`** (матрица, прозрачность, скалярные значения) — нормативная форма для `FadeIn/FadeOut`, `Shift`, `Scale`, `Rotate`. **Контуро-порождающие анимации** (`Transform`, `ReplacementTransform`, `Create`, `Write`) дополнительно реализуют zero-alloc-форму **`interpolatePath(alpha: Float, out: FlatVectorPath)`**, пишущую интерполированную геометрию в предвыделенный плоский контейнер (5.9 п.2). Из двух форм горячий путь использует ту, что соответствует типу анимации.
- **Rate-функции** — **полный каталог ManimCE один в один** (решение D-14). Это часть публичного API ManimCE, а мы его зеркалим (D-3), поэтому минимального набора недостаточно: реализуются все функции из `manim/utils/rate_functions.py`. Полный перечень — Приложение D. На старте (Спринт 1) фактически используется только `smooth`, остальные добавляются по мере надобности, но целевой набор — весь.
- **Конкретные анимации** (по спринтам): `Create`, `FadeIn`, `FadeOut`, `Shift`, `Scale`, `Rotate`, `Transform`, `ReplacementTransform`, `Write`, `AddTextLetterByLetter`.

### 5.4. Сцена и цикл рендеринга

`Scene` владеет списком объектов и очередью анимаций. Логически на каждом кадре сцена продвигает время, вычисляет `alpha` для активных анимаций, прогоняет его через rate-функцию, вызывает `interpolate`, затем перерисовывает кадр. Целевая частота — 60 FPS.

**Критично: вычисления и отрисовка идут НЕ на UI-потоке.** Здесь две отдельные ловушки. Первая — наивный `while`-цикл на главном потоке вызвал бы ANR (зависание). Вторая, тоньше: `Choreographer` по умолчанию вызывает свой колбэк **тоже на главном потоке**, поэтому если внутри него выполнять всю математику кадра (интерполяция путей, выравнивание, матрицы, вёрстка текста), при выходе за бюджет кадра (~16.67 мс при 60 FPS) начинается jank и, что хуже, тормозится обработка касаний — то есть теряется интерактивность, главное преимущество KManim.

**Решение (D-17 уточнён, D-22): архитектура игрового движка с выделенным `RenderThread`.** Вычисления сцены и команды отрисовки выполняются на отдельном потоке рендеринга поверх `SurfaceView` (захват канваса через `SurfaceHolder.lockHardwareCanvas()`, рисование из фонового потока, синхронизация с VSYNC при `unlockCanvasAndPost()`). UI-поток занимается только приёмом пользовательского ввода и кладёт события в **потокобезопасную очередь** сцены. Для 3D роль поверхности берёт на себя Filament на том же выделенном потоке.

Шаг по времени остаётся **дельтой реального времени между кадрами** (не жёсткий `+1/60`) — это делает анимацию устойчивой к просадкам частоты. **`Choreographer` является источником кадрового такта:** `dtNanos` берётся как дельта между соседними `frameTimeNanos` его колбэка (`postFrameCallback`), проброшенного на `RenderThread`; сама работа выполняется на `RenderThread`, а не в колбэке на UI.

> **Нюанс по третьему аудиту (уточнено в 0.17, D-37).** Источник кадрового такта — VSYNC через `Choreographer.frameTimeNanos`, **а не** блокировка `lockHardwareCanvas()`. Блокировка `dequeueBuffer` внутри `lockHardwareCanvas()` — это back-pressure `BufferQueue` (поток ждёт, когда освободится буфер при заполненной очереди тройной буферизации): она служит лишь страховкой от забегания продьюсера на 1–2 кадра вперёд, но **не** является основным пейсингом (полагаться на неё как на VSYNC ненадёжно — при тройной буферизации поток успевает прогнать кадры до блокировки). Но пока поток «спит» на этом вызове, нельзя допустить задержку ввода: **очередь ввода обязана быть строго неблокирующей** на стороне продьюсера (`ConcurrentLinkedQueue` без локов) и разбираться в начале кадра. Блокирующие участки в обмене UI↔`RenderThread` запрещены.

Из этого следуют требования к контракту `Scene`:
- Интеграция с жизненным циклом Android (`Activity`/`Fragment`): `RenderThread` и подписка на кадры запускаются при появлении на экране (`Surface` создана) и останавливаются при уходе (`onPause`/`surfaceDestroyed`), иначе поток и рендеринг утекут. **При `surfaceDestroyed` `Scene` дополнительно прогоняет `onDetach` по дереву объектов** (освобождение GPU-хэндлов/билбордов, 5.5.7/D-40), иначе ресурсы утекут при пересоздании `Surface`.
- `play(...)` не блокирует: кладёт анимацию в потокобезопасную очередь; продвижение происходит на `RenderThread`.
- Весь обмен между UI-потоком (ввод) и `RenderThread` (состояние сцены) — только через потокобезопасные **неблокирующие** структуры.
- **Обратная связь к UI:** Если `RenderThread` нужно уведомить UI-поток (например, о завершении анимации для показа кнопки "Далее"), используются асинхронные неблокирующие механизмы (например, отправка событий через `Handler(Looper.getMainLooper())` или Kotlin Coroutines Channels). Вызывать UI-методы напрямую из `RenderThread` строго запрещено.

Обновлённая концептуальная схема — Приложение B. Решения D-17 и D-22.

### 5.5. Абстракция рендерера (центральное решение)

#### 5.5.1. Backend-нейтральные данные

Ни один из этих типов не знает про Canvas, GL или Vulkan:

- `VectorPath` — собирательный термин для 2D-геометрии (набор подпутей из кубических Безье); **не отдельный класс**, а обобщение двух нормативных представлений — `TopologicalPath` и `FlatVectorPath` (раздел 5.2.1, D-34).
- `Mesh` — 3D-геометрия (массивы вершин и индексов).
- `Paint` — стиль (цвет, заливка/обводка, толщина линии).
- `Camera` — **логические** матрицы вида и проекции (`view`, `projection`) — **только для 3D** (`Renderer3D`). 2D-сцена использует отдельную сущность `SceneFrame`/`Camera2D` (см. 5.5.6); `Renderer2D` при этом остаётся вьюпорт-агностичным.

#### 5.5.2. Непрозрачные хэндлы ресурсов

GPU-ресурсы (буферы, текстуры) представлены непрозрачными хэндлами (`MeshHandle`, `TextureHandle`). Объект держит хэндл; реальным ресурсом владеет бэкенд. **Объект никогда не хранит сырой GL-id** — иначе смена бэкенда сломала бы всё.

#### 5.5.3. Интерфейсы-порты

- `Renderer2D`: `fillPath`, `strokePath`, `drawText`.
- `Renderer3D`: `upload(mesh): MeshHandle`, `release(handle)`, `setCamera(camera)`, `draw(handle, material, model)`.
- `RenderContext`: даёт доступ к `r2d` и `r3d`.

Полные сигнатуры — Приложение A.

#### 5.5.4. Три условия безболезненной смены бэкенда

Чтобы переход (например GL ES → Vulkan, или → Filament) не затрагивал ядро, в абстракцию заложены три вещи:

1. **Непрозрачные хэндлы ресурсов** (см. 5.5.2).
2. **Камера отдаёт логические матрицы**, а конкретный бэкенд внутри себя адаптирует различия NDC: у OpenGL глубина в диапазоне `[-1, 1]`, у Vulkan — `[0, 1]`; у Vulkan ось Y в NDC направлена вниз (начало кадрового буфера — верхний левый угол), у GL — вверх. Объекты и камера об этих различиях **не знают**.
3. **Подача команд скрыта за `beginFrame()` / `endFrame()`**, чтобы разница между immediate-режимом GL и командными буферами Vulkan не протекала наружу.

#### 5.5.5. Точка смены бэкенда

Смена бэкенда — это **одна строка в фабрике**; ни DSL, ни объекты, ни анимации не трогаются:

```kotlin
val r3d: Renderer3D = if (useVulkanBackend) FilamentRenderer3D() else GLES3Renderer3D()
```

#### 5.5.6. 2D-камера (SceneFrame / Camera2D) — решение D-38

`Camera` (5.5.1, Приложение A) — это **3D**-матрицы `Mat4`. Для 2D-пайплайна (Спринты 1–6) вводится отдельная backend-нейтральная сущность ядра `manim-core` — **`SceneFrame`/`Camera2D`** с полями `frameWidth`/`frameHeight`/`center` (паритет с ManimCE `frame_width`/`frame_height`; дефолт — **14.222 × 8.0** юнита при 16:9). Им владеет `Scene`.

**Контракт.** `Scene` вычисляет вьюпорт-`Mat3` (сцена→пиксели, с учётом размера поверхности и аспекта; при несовпадении аспекта — letterbox) и применяет его **до** per-object трансформы: итоговый `Mat3`, передаваемый в `Renderer2D.fillPath/strokePath`, равен `viewport ∘ objectTransform`. Так порт `Renderer2D` **остаётся вьюпорт-агностичным** (камеры в нём нет), а преобразование сцены — ответственность ядра. Обратное преобразование экран→сцена (инверсия вьюпорт-`Mat3`) используется для хит-тестинга/интерактивности (5.10).

**Следствия:** в Спринте 1 единица измерения — manim-юнит, отображаемый через `SceneFrame` (иначе пиксельный размер «круга радиусом 2f» не определён); добавляется golden-инвариант корректности юнит→пиксель. Анимации `MoveCamera`/zoom (Спринт 8) — это анимации над `SceneFrame.center`/`frameWidth` поверх уже введённого статического фрейма, а не место первого появления камеры.

#### 5.5.7. Жизненный цикл ресурсов (решение D-40)

Симметрично принципу zero-alloc горячего пути (5.9) фиксируется дисциплина освобождения ресурсов **вне** горячего пути:

- **Инвариант владения:** каждому `upload(mesh)` соответствует ровно один `release(handle)`; каждому `Bitmap`, взятому из пула билбордов (5.7), — `recycle()` при уничтожении пула. Островок из 5.7 обобщается на все GPU-ресурсы.
- **Teardown у `MObject`:** добавляется `open fun onDetach(ctx: RenderContext)`, который `Scene` вызывает (а) при удалении объекта из сцены и (б) при `surfaceDestroyed`. Реализация рекурсивна по `submobjects` (по образцу `render()`, без лямбд); 3D-объекты в нём вызывают `ctx.r3d.release(handle)`, объекты с билбордами возвращают `Bitmap` в пул. Цикл teardown — **не** горячий путь, аллокации в нём допустимы.
- **При `surfaceDestroyed`** `Scene` не только останавливает `RenderThread`, но и прогоняет `onDetach` по дереву — иначе при пересоздании `Surface` (поворот экрана) `MeshHandle`/`TextureHandle` утекут.
- **Кэш распарсенных формул:** для основного (compile-time/asset) пути геометрия глифов `MathTex` кэшируется со временем жизни объекта и сбрасывается в его `onDetach`; рантайм-fallback (D-27) держит долгоживущий дисковый кэш в пределах сессии.

### 5.6. DSL

DSL строится средствами Kotlin: **lambda-with-receiver** (`scene { ... }`, где `this` — это `Scene`), **extension-функции** (фабрики объектов), **перегрузка операторов** (векторная арифметика, например `RIGHT * 2f`), **infix-функции** (`circle moveTo ORIGIN`). Цель — чтобы пользовательский код читался декларативно и близко к ощущению Python-Manim. Пример целевого синтаксиса — Приложение C.

**Связь с Jetpack Compose (и почему мы не строим поверх него).** Синтаксически DSL родственен Compose — оба стоят на lambda-with-receiver (`scene { circle(...) }` — тот же механизм, что `Column { Text(...) }`). Но модель исполнения выбрана иной сознательно. Compose реактивен и описывает UI *при данном состоянии* — рекомпозиция скрывает ось времени, он про «сейчас». KManim императивно-временной: ось времени — главная (последовательность `play(...)`), и точный контроль `alpha` — это весь смысл. Построить KManim поверх Compose (рисуя в `Canvas` композабла и гоняя `Animatable`) технически возможно, но тогда мы унаследовали бы модель времени Compose, заточенную под UI-переходы, а не под покадровую математическую анимацию. Поэтому синтаксическое сходство приветствуется, а собственную модель времени (на выделенном `RenderThread`, раздел 5.4) мы сохраняем.

**Контракт `.animate` (по третьему аудиту).** Конструкция `circle.animate.shift(...)` (взята из ManimCE ради паритета) под капотом создаёт **прокси**, перехватывающий изменения свойств для построения анимации. Чтобы это не порождало утечек и непредсказуемого поведения, контракт жёсткий: `.animate` — **одноразовый билдер**, валидный только непосредственно в момент передачи в `play(...)`; его **нельзя** сохранять в переменную, переиспользовать или вызывать вне потока сцены. Нарушение — ошибка использования, а не поддерживаемый сценарий (зафиксировать в документации DSL).

### 5.7. Компоновка 2D и 3D

Обычная 2D-сцена идёт целиком через Canvas/Skia (решение 4.6). Для `ThreeDScene` важная поправка по итогам аудита: **у Filament (как и у чистого GL ES / Vulkan) нет встроенного векторного рендерера** — он рисует полигональные меши и материалы, но не произвольные кривые Безье со сглаживанием. Поэтому формулировка «2D-оверлеи рисуются тем же GPU-векторным рендером» нереализуема без отдельного сложного решения и заменяется на конкретный механизм.

**Решение (D-18): offscreen-текстура Canvas → Filament.** В `ThreeDScene` все 2D-объекты и оверлеи (подписи осей, формулы, плоские `VMobject`) рисуются стандартным `android.graphics.Canvas` в offscreen-`Bitmap`/текстуру, а затем эта текстура накладывается как материал на плоский quad/billboard в 3D-сцене Filament. Плюсы: идеальное сглаживание (за счёт Skia), переиспользование всего 2D-кода, предсказуемые 60 FPS. Цена: нет честного интерливинга, когда 3D-объект протыкает 2D-плоскость насквозь — для математических презентаций это почти никогда не требуется, и в первой версии мы это ограничение принимаем сознательно.

**Нюанс производительности (дополнено по второму аудиту, D-18).** 2D-оверлеи анимируются, и наивная перезаливка одной большой текстуры на весь экран каждый кадр упрётся в пропускную способность шины памяти: на планшете с QuadHD текстура 2048×2048, заливаемая покадрово (`glTexSubImage2D`/Vulkan-буферы), это ~5–12 мс на кадр — почти весь бюджет кадра плюс троттлинг. Поэтому:
- **Мелкие билборды вместо одной текстуры.** Каждый 2D-объект (или группа) — своя небольшая текстура. **Статичные** элементы (оси, сетка, готовые подписи) рендерятся в текстуру один раз и больше не заливаются. Покадрово перезаливается только текстура **конкретного анимирующегося** объекта (например, формула 256×64).
- **Пул `Bitmap` фиксированных размеров + `Texture.setImage`-copy (D-18, пересмотрено в 0.8, уточнено в 0.17/D-37).** Третий аудит показал, что zero-copy через `AHardwareBuffer` требует ручной синхронизации графическими барьерами (sync fences) на стыке Skia→Filament: если Filament прочитает текстуру до того, как Skia дорисовала, будут артефакты (мерцание, старые кадры), а надёжная синхронизация барьеров на Kotlin/NDK платформозависима и хрупка (Adreno/Mali). Поэтому для v1 берётся **прагматичный путь**: пул небольших `Bitmap` фиксированных размеров (128×32, 256×64, 512×128); анимируемый объект рисуется обычным Canvas в свободный `Bitmap` из пула, затем `Texture.setImage`. **Основание безопасности — не «двойная буферизация» сама по себе:** `Texture.setImage` принимает `PixelBufferDescriptor`, и Filament **копирует** переданный буфер, поэтому `Bitmap` из пула можно безопасно перерисовывать в следующем кадре (для малых/средних текстур <0.2 мс). Отдельно — **in-flight риск**: чтобы материал не сэмплировал текстуру, перезаписываемую в том же кадре, для анимируемых билбордов держим на слот пула **две Filament-текстуры и чередуем их по кадрам (ping-pong: сэмплируем одну, заливаем другую)** либо опираемся на release-callback `PixelBufferDescriptor`. Выбор подтверждается device-spike (оговорка D-28). `AHardwareBuffer` оставлен как возможная оптимизация на потом, если профайлинг упрётся в шину.
- **`Bitmap` из пула выделяется один раз и перерисовывается в тот же буфер** — не пересоздаётся каждый кадр (см. 5.9). **Жизненный цикл пула:** Пулом владеет `Renderer3D` (или `RenderContext`). При уничтожении поверхности (`surfaceDestroyed` / `onDestroy`) рендерер обязан очистить пул и вызвать `bitmap.recycle()` для всех текстур, чтобы избежать утечек памяти (OOM).

Альтернативы (CPU-тесселяция путей в меши; шейдерный GPU-векторный рендерер вроде Loop–Blinn / Vello) рассмотрены и отложены: первая грузит CPU при анимации путей и угрожает 60 FPS, вторая чрезмерно сложна для интеграции с Filament. Конкретная организация `ThreeDScene` детализируется на Спринте 7.

### 5.8. Абстракция движка формул (TexEngine)

LaTeX подключается к ядру за интерфейсом — ровно по инварианту 4.5, как и рендер-бэкенд. Вводится отдельный внутренний интерфейс **движка формул**:

`TexEngine: (formula: String) -> TopologicalPath`

Его задача единственная — превратить строку формулы в backend-нейтральный `TopologicalPath` (глифы-как-пути; объектная форма, которая компилируется в `FlatVectorPath` для горячего пути, см. 5.2.1). Всё, что выше (объект `MathTex`, анимация `Write`, сцена), знает только про backend-нейтральную геометрию (`TopologicalPath`/`FlatVectorPath`, D-34) и **не** знает, какой движок её породил.

**Следствие — заменяемость.** Смена движка формул сводится к тому же приёму, что и смена рендер-бэкенда: пишется другая реализация `TexEngine`, меняется одна строка в фабрике, ничего выше не трогается.

**Условие.** Заменяемость не бесплатна — она держится на дисциплине: конкретный движок не должен «протекать» глубже `TexEngine` внутрь `MathTex` или сцены. Граница проводится там же, где и остальные швы проекта. Контракт — Приложение A.

**Выбор движка: KaTeX (а не JLaTeXMath).** Изначально планировался JLaTeXMath, но он намертво завязан на Java AWT (`java.awt.Graphics2D`, `TextLayout`, `Path2D`), которого в Android SDK нет вообще; адаптация без AWT по объёму сравнима со всем движком. KaTeX (JS-библиотека) рендерит формулу в SVG, а компактный парсер SVG-путей (команды M, L, C, S, Z) транслирует контуры глифов в наш `VectorPath`. KaTeX чище, полнее по стандарту LaTeX и точнее; парсер пишется за дни. Цена — KaTeX написан на JS, значит нужен JS-движок. Вопрос лишь в том, **когда** этот движок работает — и здесь ключевое решение 0.9.

**Основной путь — compile-time раскладка (решение D-20, пересмотрено в 0.9).** В скомпилированном Kotlin-DSL формулы — почти всегда литералы (`mathTex("E = mc^2")`), известные на этапе сборки. Поэтому KaTeX прогоняется **не на устройстве в рантайме, а на машине разработчика во время сборки**: Gradle-плагин обходит формулы-литералы, рендерит их через KaTeX под Node, парсит в `VectorPath` и кладёт готовую геометрию в ассеты APK. В рантайме формула **не парсится** — `MathTex` грузит готовый `VectorPath` из ассета. Следствия: **JS-движок (QuickJS + `katex.min.js`, ~300–500 КБ) в APK не входит вообще**, если в приложении нет динамических формул; ноль риска фриза холодного старта; проще сборка под разные ABI (про что беспокоился аудит); меньше вес APK. Обоснование — наблюдение из обсуждения: в реальном времени пользователь меняет *параметры* (положение, масштаб, значения на осях), а *структура* формулы (`\sum`, дроби, индексы) в рантайме практически не меняется, то есть формулы — статический, известный на сборке контент.

**Опциональный fallback — рантаймовый JS (решение D-27, переформулировано в 0.9).** Нужен только для **динамических** формул, где строка неизвестна на сборке (например, коэффициент внутри формулы привязан к ползунку: `mathTex("y = ${a}x^2")` с анимируемым `a`). Тогда подключается рантаймовая реализация `TexEngine` на встраиваемом JS-движке. В качестве движка фиксируется готовая библиотека `app.cash.quickjs:quickjs-android` (или аналог), чтобы избежать самостоятельной сборки движка через NDK. В этом — и только в этом — режиме relevantны меры против холодного старта: асинхронный прогрев движка на старте приложения (`Application.onCreate`), дисковый кэш `VectorPath` по строковому ключу, и парсинг формулы один раз (анимация идёт над готовой геометрией, без перепарсинга на кадр). Поддержка динамических формул в v1 не обязательна (O-7) — но шов это позволяет добавить позже без правок ядра. Частая альтернатива даже для динамики: предрендерить на сборке глифы-кирпичики (цифры, знаки) и собирать из них значение в рантайме, тоже без JS.

**Архитектурно** обе реализации — это один и тот же интерфейс `TexEngine: String → TopologicalPath` (раздел 5.2.1): compile-time-реализация берёт готовое из ассетов, рантаймовая дёргает JS. Что выше шва (`MathTex`, `Write`, сцена) — не знает, какая из них работает. JLaTeXMath остаётся теоретически возможной третьей реализацией, но не используется.

**Классы формул: `Tex` и `MathTex` (паритет, D-42).** ManimCE различает два публичных класса — `Tex` (LaTeX в text-режиме: обычный текст с возможными формулами) и `MathTex` (math-режим: формула). KManim зеркалит оба: это `VMobject` поверх `TexEngine`, различающиеся режимом раскладки (text/math). `MathTex` поддерживает **индексацию подвыражений** (`substringsToIsolate` → разбиение на `submobjects`) — это условие выполнимости `Transform`/`TransformMatchingTex` между частями формулы (D-24) и объектного `matchPoints`. Оба класса и индексация заводятся в `API_PARITY.md` (Спринт 5).

### 5.9. Производительность и горячий путь (сквозной принцип)

Цель «стабильные 60 FPS» — не следствие отдельных оптимизаций, а архитектурный инвариант, который пронизывает весь движок. Определение: **горячий путь** — это всё, что выполняется покадрово (продвижение анимации, интерполяция, обход дерева объектов, формирование команд отрисовки). Принцип: **горячий путь проектируется аллокационно-чистым; всё дорогое кэшируется и инвалидируется по dirty-флагу; однородная геометрия батчится.** Конкретно:

1. **Zero-allocation в кадровом цикле.** Цикл, исполняемый 60 раз в секунду, не должен порождать мусор: никаких временных лямбд, автобоксинга, новых коллекций на кадр. GC-микропаузы от десятков тысяч короткоживущих объектов в секунду — прямая причина микрофризов (это и есть риск, вскрытый аудитом). Состояние цикла выделяется заранее.
2. **Flat-memory геометрия (через двухуровневую модель).** В горячем пути интерполяция идёт по плоскому `FlatVectorPath` (`FloatArray`), а не по дереву объектов; объектный `TopologicalPath` используется только для холодных операций над формой (раздел 5.2.1, D-23). Контуро-порождающая интерполяция пишет в **предвыделенный контейнер** (`interpolatePath(alpha, out: FlatVectorPath)`, D-35), а не возвращает новый путь.
3. **Пулы и out-параметры (D-36).** Часто создаваемые мелкие объекты — `Vector2`, матрицы (`Mat3`/`Mat4`/`Transform`) — это **mutable дата-классы**, берутся из пулов и/или результат пишется в предвыделенный `out`-экземпляр (как `interpolatePath(alpha, out)`), а **не** аллоцируются на кадр. Они **не** `value class` (мультиполевой value class нестабилен на Kotlin 2.0, а пул требует identity+mutable — что несовместимо с иммутабельной value-обёрткой). Единственный value-class-кандидат — однополевой `Color` (ARGB `Int`), и только вне дженериков/nullable/коллекций.
4. **Кэш `Paint`.** `Paint` (и системный `android.graphics.Paint` под ним) кэшируется на объекте и переиспользуется, а не создаётся в каждом `draw`.
5. **Разделение «геометрия» и «трансформа» через dirty-флаг.** Локальная геометрия Безье пересчитывается только при изменении формы (дорого, редко); при простом перемещении/масштабе меняется лишь матрица (дёшево, часто). Путь кэшируется и перестраивается только по флагу инвалидации — иначе `Transform` и статичная сетка жгут CPU впустую.
6. **Батчинг однородной геометрии.** Координатная сетка / `Axes` / `NumberPlane` — это сотни линий; они рисуются одним батчем (один путь со множеством подпутей, один `Paint`), а не как тысячи отдельных `MObject` со своим `draw`.
7. **Без пересоздания буферов.** Текстуры билбордов и `Bitmap` под них (раздел 5.7) аллоцируются один раз и перерисовываются в тот же буфер.

Эти правила отражены в Приложениях A и B и в критериях спринтов (профилирование частоты и аллокаций — часть Definition of Done там, где это применимо).

### 5.10. Модель ввода и интерактивности (решение D-44)

Интерактивность объявлена ключевым преимуществом KManim (1.2, 4.2), а потоковая модель (5.4) уже предусматривает неблокирующую очередь ввода. Контракт фиксируется так (глубина интерактивности в v1 опциональна, но сам контракт зафиксирован, а не оставлен открытым):

- **Тип события — доменный `InputEvent`** (нормализованные координаты сцены + фаза down/move/up), а **не** сырой `MotionEvent` — это держит шов переносимым (D-26). UI-поток только адаптирует `MotionEvent` → `InputEvent`.
- **Отдельная очередь.** Ввод идёт через **самостоятельную** `ConcurrentLinkedQueue<InputEvent>`, отличную от очереди анимаций (либо общая MPSC-структура с типизированным конвертом) — чтобы потоки событий и анимаций не смешивались.
- **Разбор — на `RenderThread`** в начале кадра (как и сказано про неблокирующую очередь в 5.4); преобразование экран→сцена — через обратную вьюпорт-`Mat3` 2D-камеры (5.5.6).
- **Хук объекта.** Минимальный контракт доставки/hit-testing — `MObject.hitTest(...)`/`onEvent(...)`, ЛИБО явная оговорка, что в v1 интерактивность ограничена уровнем сцены. Приложение B (поля очереди/`play`) обновляется синхронно при реализации.

Чтобы каркас Спринта 0 строился однозначно (решение D-46):

| Gradle-модуль | namespace / пакет | Тип модуля / convention-плагин |
|---------------|-------------------|--------------------------------|

- **SDK/JDK:** `compileSdk = 34`, `targetSdk = 34`, `minSdk = 34` (из 1.6/D-10); `JDK 17`, `jvmTarget = "17"`, `sourceCompatibility/targetCompatibility = 17` (требование AGP 8.4+).
- **Структура:** модули — плоско в корне репозитория; корневой `settings.gradle.kts` содержит `includeBuild("build-logic")` и `include(...)` всех модулей. Конкретные версии зависимостей — раздел 7.1.

## 7. Технологический стек

| Слой | Технология | Роль и обоснование |
|------|-----------|--------------------|

## 8. Стратегия тестирования

**Подход — Test-Driven Development.** Каждый спринт завершается зелёными тестами.

**Почему именно такой стек (и почему не Kotest).** На Android тесты делятся на два рода, и это разделение определяет выбор инструментов:

- **Local unit-тесты** — гоняются на JVM, без устройства, мгновенно. Подходят для чистой логики.
- **Instrumented-тесты** — гоняются на эмуляторе/устройстве, потому что им нужны настоящие Android-классы.

Наши golden-image тесты рендерят в настоящий `android.graphics.Bitmap` через `Canvas`, а это Android-классы (в обычном JVM-unit-тесте они застаблены и возвращают пустышки). Значит golden-тесты **обязаны** быть instrumented-тестами и идут через `androidx.test` (раннер `AndroidJUnit4`), а не через Kotest. Kotest же в инструментальную экосистему Android ложится плохо и без выигрыша, а для JVM-логики его матчеры и property-тесты избыточны — то же дают JUnit5 и лёгкий jqwik. Поэтому Kotest исключён (решение D-8).

**Два уровня тестов, работают параллельно:**

1. **Логика — JUnit5 (+ jqwik для property-тестов), local unit на JVM.** Примеры инвариантов: «для любого радиуса площадь окружности, аппроксимированной кривыми Безье, сходится к πr²»; «после выравнивания двух путей число контрольных точек совпадает»; «интерполяция alpha монотонна и попадает в `[0,1]`»; коммутативность/корректность матриц во вложенных `VGroup`.
2. **Визуальный результат — golden-image тесты**, в два эшелона ради скорости (решение D-21):
   - **Быстрый эшелон — Robolectric + Roborazzi на JVM.** Гоняет скриншот-сравнения без эмулятора, за доли секунды, используя плагин `Roborazzi` с поддержкой порогов совпадения, поэтому идеально подходит на каждый коммит/в CI. **Оговорка:** Robolectric растеризует графику не гарантированно пиксель-в-пиксель с реальным Skia на устройстве, поэтому он используется для быстрого отлова регрессий, но **не является эталоном истины**. Точность Robolectric для пиксельного сравнения проверяется в Спринте 0, прежде чем на него полагаться.
   - **Эталонный эшелон — androidx.test на устройстве/эмуляторе** (раннер `AndroidJUnit4`; единый инструмент — **Roborazzi в on-device режиме**, D-46). Рисует в настоящий `android.graphics.Bitmap`, сравнивает с эталонным PNG **с допуском на сглаживание** (точное побитовое равенство недостижимо из-за анти-алиасинга). Это финальная пиксельная сверка; именно здесь фиксируются эталоны. Запускается реже — перед слиянием/релизом и для дымового теста на реальном GPU (через `connectedCheck`, а не `check`; см. 15.6).

**Что чем проверяется:** чистая логика (геометрия, тайминги, интерполяция, матрицы) — JUnit5/jqwik на JVM; внешний вид кадра — golden-image (Robolectric для скорости, устройство для истины). Они дополняют друг друга и не пересекаются. Харнесс обоих эшелонов настраивается в Спринте 0.

**Меры против нестабильных (flaky) golden-тестов.** Разные GPU (Mali, Adreno, PowerVR) по-разному применяют сглаживание в Skia, поэтому единый «допуск» легко делает тесты то зелёными, то красными без изменений в коде — а тесту, которому перестают верить, хуже, чем его отсутствию. Конкретные меры (уточнено по третьему аудиту, D-21; единый инструмент — D-46): инструмент скриншот-тестов — **Roborazzi** (единый для обоих эшелонов, on-device для эталона), с настраиваемым порогом совпадения пикселей **≥98%**; сравнение — по доле различающихся пикселей / перцептивной метрике (SSIM), а не побитово; эталонные golden-images генерируются и проверяются **только на одной зафиксированной конфигурации — `Pixel 6 Pro, Google APIs, API 34, x86_64`**, прогон эталонных тестов на произвольных машинах без соответствия конфигурации запрещён. Это закладывается в харнесс Спринта 0, иначе тесты начнут врать через месяц.

### 8.1. Универсальная верификация Time-Dependent API (Временной детерминизм)

Для тестирования **любого API, зависящего от времени** (анимации во времени, апдейтеры `addUpdater`, `.animate`-прокси, динамические трекеры значений, временные цепочки `play`/`wait`), категорически запрещено использовать системные часы, асинхронные корутины или `Thread.sleep()` (риск нестабильных flaky-тестов на разном железе).

Вместо этого тестовый харнесс обязан работать в режиме **дискретного детерминированного сэмплирования**: тест вручную и последовательно подаёт детерминированные временные шаги ($t_0, t_1, t_2 \dots t_n$ или дельты $dt$), вызывая интерполяцию/обновление сцены и делая golden-снимок каждой фазы. 

Этот подход даёт тройную гарантию:
1. **100% стабильность:** Тесты выполняются с побитовой предсказуемостью на любом сервере CI или слабом ноутбуке.
2. **Математическая строгость:** Доказывает корректность промежуточных состояний Безье и точность применения rate-функций (easing) во времени.
3. **Автоматическая сборка GIF/APNG:** Именно из этой гарантированной последовательности PNG-срезов CI автоматически склеивает идеальные, плавные медиа-иллюстрации для абсолютно любой страницы нашего веб-справочника `docs/`.

## 9. План разработки по спринтам

Спринты короткие. **Definition of Done каждого спринта:** (а) осязаемый артефакт — собранный APK демо-приложения + скриншот/запись результата; (б) зелёные тесты (логика + golden, где применимо); (в) обновлённый `API_PARITY.md`; (г) обновлённые зеркальные страницы документации по затронутым API и golden-тесты «manim-parity» для воспроизведённых канонических примеров (раздел 10.1); (д) обновлённые `STATUS.md` и `DEVLOG.md`, коммит и git-тег `sprint-N-done` (раздел 14).

> Если есть зелёные тесты и скриншот, значит демо-Activity собрана, и APK падает одной командой Gradle.

### Спринт 0 — Каркас
**Цель:** фундамент. Щупать пока почти нечего.
**Объём:** настройка Gradle-мультимодуля (`manim-core`, `manim-geometry`, `manim-render`, `demo-app`) через обязательный композитный билд `includeBuild("build-logic")` с convention plugins (`kmanim.jvm.library` для JVM-ядра, `kmanim.android.library`, `kmanim.android.application` — раздел 6.1) и централизованным `libs.versions.toml` (зафиксированные версии — раздел 7.1; namespace/SDK/JDK — раздел 6.1); подключение тестового стека — **JUnit5 (+ jqwik)** для JVM-логики, **Robolectric + Roborazzi** для быстрых скриншот-прогонов и **androidx.test + Roborazzi (on-device режим)** для эталонной пиксельной сверки на фиксированном эмуляторе; настройка golden-харнесса в обоих эшелонах (порог ≥98%, эталон на `Pixel 6 Pro / API 34 / x86_64`); **заведение Gradle-задачи `generateMirrorDocs` в `build-logic`** (Kotlin-генератор без Node, D-45) — генерирует каркас `docs/` (`index`, `examples.html`, `tutorials/index.html`, `guides/`, `reference.html`) со 100% описью классов/страниц ManimCE в статусе ⬜ и завершается успехом (медиа — плейсхолдеры; GIF/APNG-энкодер подключается со Спринта 1); заведение `API_PARITY.md`; **заведение `STATUS.md` и `DEVLOG.md` и фиксация ритуала сессии (раздел 14) как обязательного с первого дня**.
**Артефакт:** пустой APK запускается; один тривиальный тест зелёный; golden-харнесс проверен на одном чёрном квадрате.
**Проверки по аудитам** — разделены на два класса с явным критерием прохождения:
*Автоматизируемые на эталонном эмуляторе, входят в гейт (блокируют `sprint-0-done`):* (1) на простом эталоне (чёрный квадрат) измерить долю расхождения Robolectric vs эталонного эмулятора и задокументировать решение «доверять/нет» в `DEVLOG.md` (D-21); (2) instrumented golden рендеринга на фоновом потоке через `SurfaceView` (`lockHardwareCanvas`) на `Pixel 6 Pro / API 34 / x86_64`, совпадение ≥98% — фундамент потоковой модели (D-22); (3) каркас точки асинхронного прогрева JS-движка на старте приложения — обычный unit-тест (D-27).
*Device-spike (требует физического устройства, НЕ входит в `./gradlew check`, НЕ блокирует `sprint-0-done`):* (4) дымовой тест совместимости Filament с `SurfaceView`/потоковой моделью и перезаливкой текстур билбордов — оговорка D-28; критерий — ручной отчёт в `DEVLOG.md`; обязательное подтверждение интеграции — критерий Спринта 7.

### Спринт 1 — Первый живой круг ← *первый «вау»*
**Цель:** сквозной вертикальный срез от математики до пикселей на экране.
**Объём:** backend-нейтральная математика (`Vector2`, `CubicBezier`, `Transform`); классы `MObject` / `VMobject` (с flat-memory `FlatVectorPath`, раздел 5.9); `Circle` через аппроксимацию Безье; **2D-камера `SceneFrame`** (D-38) — единица измерения = manim-юнит, отображаемый через вьюпорт-`Mat3` (без неё пиксельный размер «круга радиусом 2f» не определён); интерфейс `Renderer2D` + первая реализация `CanvasRenderer2D`; анимация `Create` + rate-функция `smooth` (из namespace `RateFunctions`, D-43); **модель времени сразу на выделенном `RenderThread` поверх `SurfaceView`** (не на UI-потоке, такт от `Choreographer.frameTimeNanos`, шаг по дельте, раздел 5.4/D-37).
**Артефакт:** **синий круг плавно прорисовывается и едет вправо, 60 FPS.**
**Тесты:** сходимость площади круга (property-based); корректность интерполяции alpha; golden-снимок финального кадра.
**Уточнение по аудиту:** круг описывать четырьмя кубическими сплайнами с константой каппа `K ≈ 0.5522847` (контрольные точки на расстоянии `K·r` от опорных) — это стандартная точная аппроксимация окружности Безье.

### Спринт 2 — Геометрия и базовые анимации
**Цель:** набор примитивов и базовый словарь движений; оформление DSL.
**Объём:** объекты `Square`, `Line`, `Polygon`, `Dot`, `Arc`; анимации `FadeIn`, `FadeOut`, `Shift`, `Scale`, `Rotate`; DSL обретает форму (`scene { ... play(...) ... }` через lambda-with-receiver); группировка `VGroup`.
**Артефакт:** демо, где несколько фигур появляются, двигаются и крутятся в цепочке.
**Тесты по аудиту:** property-тесты (jqwik) на вложенные трансформации `VGroup` — проверка корректности накопления матриц перехода, чтобы ошибки во вложенных группах не копились незаметно.
**Журнал API:** заметно пополняется.

### Спринт 3 — Transform (морфинг) ← *второй «вау»*
**Цель:** плавное превращение одной фигуры в другую.
**Объём:** сопоставление точек двух путей (выравнивание числа контрольных точек путём подразбиения того, у которого их меньше) и интерполяция соответствующих контрольных точек; анимации `Transform`, `ReplacementTransform`. Алгоритмы сопоставления пишутся на объектном `TopologicalPath`, а покадровая интерполяция идёт по скомпилированному `FlatVectorPath` (раздел 5.2.1) — это и есть причина, по которой двухуровневая модель введена до Спринта 3.
**Артефакт:** **круг плавно перетекает в квадрат и обратно.**
**Тесты:** равенство числа точек после выравнивания; монотонность морфинга.
**Ограничение первой версии (по аудиту):** надёжный морфинг гарантируем для простых односвязных замкнутых контуров; сложные топологии (разное число «дырок», напр. «8» → «1») выносим за рамки v1 и фиксируем в `API_PARITY.md` как 🟡.
**Обязательно даже для простых контуров (второй аудит):** (1) **направление обхода** — перед интерполяцией сверять ориентацию контуров (по/против часовой) и при несовпадении реверсировать один из путей, иначе фигура «выворачивается наизнанку»; (2) **рост подпутей** — если у цели подпутей больше, недостающие должны «вырастать» из центров существующих (scale-from-centroid), а не прилетать из точки (0,0).
**Контракт расширения (уточнено в 0.17, D-24):** (а) `VMobject.matchPoints(other)` — **метод самого объекта** (прямой паритет с ManimCE `Mobject.match_points`): выравнивает число и позиции контрольных точек, копируя геометрию `other` в текущий объект; логически относится к холодному `TopologicalPath` (5.2.1), где уже живут выравнивание/реверс/подразбиение. (б) Для ручного сопоставления **частей** при сложных переходах — отдельные классы анимаций `TransformMatchingShapes`/`TransformMatchingTex` (паритет с ManimCE; заводятся ⬜ в `API_PARITY.md`, roadmap Спринт 8+), работающие поверх дерева `submobjects`. **Не** вешать `matchPoints` на `Transform` как билдер — это исказило бы семантику одноимённого метода ManimCE (принцип паритета D-3, оговорка 4.7).

### Спринт 4 — Текст
**Цель:** текст и его анимации, с разделением на два класса (раздел 5.2, D-19).
**Объём:** `TextLabel` — растровый текст через `StaticLayout`/`Paint.drawText` (быстрый, переносы, эмодзи, шрифты), поддерживает `FadeIn`/`FadeOut`/`Shift`/`Scale`. `VectorText` — контурный текст через `Paint.getTextPath(...)` → `VectorPath` (это `VMobject`), поддерживает `Write`/`Create` (прорисовка штрихом) и `Transform`. Анимации `Write`, `AddTextLetterByLetter` работают именно над `VectorText`.
**Артефакт:** заголовок (`VectorText`) печатается по буквам штрихом над анимацией из Спринта 3.
**Заметка:** разделение зафиксировано на уровне ТЗ заранее, чтобы не упереться в тупик «растровый текст нельзя анимировать контуром».

### Спринт 5 — LaTeX ← *формулы: сердцевина матбиблиотеки*
**Цель:** формульная вёрстка появляется раньше графиков и 3D — это математическая библиотека, формулы в ней первичны.
**Объём:** интерфейс `TexEngine` (раздел 5.8) и его **compile-time реализация** в `manim-latex` (Gradle-плагин: KaTeX под Node → `VectorPath` в ассеты); объект `MathTex`. Переиспользуется контурный фундамент Спринта 4 (`VectorText`/`VectorPath`) и анимация `Write`.
**Подэтап 5а (compile-time, основной путь, D-20):** Gradle-плагин, который на сборке находит формулы-литералы, прогоняет их через KaTeX под Node, парсит SVG-пути (M, L, C, S, Z) в `VectorPath` и кладёт в ассеты APK. В рантайме JS не участвует, движок в APK не входит. Это и заменяет прежний план адаптации JLaTeXMath, и снимает риск холодного старта.
**Подэтап 5б (опционально, fallback):** рантаймовая реализация `TexEngine` на QuickJS+KaTeX — только если в v1 решим поддержать динамические формулы (O-7); тогда работают прогрев на старте и дисковый кэш (D-27). По умолчанию в v1 можно не делать.
**Артефакт:** **формула LaTeX (например, теорема Пифагора) прорисовывается на экране штрихом** через `Write`.
**Тесты:** `TexEngine` на корректной строке возвращает непустой `TopologicalPath` (local unit); **негативные кейсы** (D-41): невалидная формула-литерал ⇒ падение задачи плагина с непустым диагностическим сообщением (compile-time), а в рантайм-режиме ⇒ `Result.failure`/`TexParseException` и видимый плейсхолдер, а не пустой путь; SVG-команда вне поддержанного подмножества ⇒ выбранное поведение (нормализация либо ошибка сборки); golden-снимок отрендеренной формулы.
**Заметка:** это первая проверка `TexEngine`-шва — по тому же принципу, по которому Спринт 7 проверяет рендер-шов.

### Спринт 6 — Координаты и графики
**Цель:** «как у 3Blue1Brown».
**Объём:** `NumberLine`, `Axes`, `NumberPlane`; построение функций (`plot { x -> sin(x) }`), `ParametricFunction`; анимация построения графика. Подписи осей могут использовать `MathTex` из Спринта 5.
**Артефакт:** оси с плавно прорисовывающейся синусоидой.
**Оптимизация по аудиту:** адаптивный шаг дискретизации функции — мельче там, где кривизна графика больше; это держит качество кривой без раздувания числа точек (и без просадки FPS на плотных графиках).

### Спринт 7 — Шов 3D (закладка реализуется)
**Цель:** реализовать `Renderer3D` по-настоящему и **проверить главную гипотезу абстракции**.
**Объём:** реализация `Renderer3D` на **Filament** (зафиксировано, D-28); `ThreeDScene`, `ThreeDAxes`, простая `Surface`. 2D-оверлеи внутри 3D-сцены — через **offscreen-текстуру Canvas → Filament** (раздел 5.7, D-18), а не через несуществующий GPU-векторный рендерер.
**Ключевая проверка:** 2D-ядро и DSL **не меняются ни на строку**. Это формальный критерий корректности шва (раздел 5.1, 5.5).
**Уточнение по аудиту:** различия NDC (ось Y вниз у Vulkan, вверх у GL; диапазон глубины) изолировать строго внутри адаптера `Renderer3D` — наружу они не протекают (раздел 5.5.4).
**Артефакт:** вращающаяся 3D-поверхность с плоской подписью-оверлеем; подтверждение, что дорога к Vulkan / XR открыта.

### Спринт 8+ — Дальнейшее расширение
**Цель:** дальнейший рост по приоритету.
**Объём:** определяется `API_PARITY.md` — что покажет наибольший разрыв с «тем, что хотим анимировать», то и берём следующим. Вероятные кандидаты: больше типов объектов, механизм обновлений (`Updater` из Manim), управление камерой, продвинутые анимации.

## 10. Журнал паритета API (`API_PARITY.md`)

Постоянный артефакт в корне репозитория. Сопоставляет API Manim (ManimCE) с нашим Kotlin-API. Одновременно — трекер прогресса к цели «100% того, что хотим анимировать» (раздел 1.5) и документация.

**Формат строки:**

| Manim (ManimCE) | KManim (Kotlin) | Статус | Заметка |
|-----------------|-----------------|--------|---------|
| `Circle(radius=1.0)` | `circle(radius = 1f)` | ✅ | Спринт 1 |
| `Transform(a, b)` | `Transform(a, b)` | 🟡 | Базовый морфинг; без выравнивания подобъектов |
| `MathTex(...)` | `mathTex(...)` | ⬜ | Запланировано, Спринт 5 |
| (видеоэкспорт через FFmpeg) | — | ❌ | Вне области; не портируем (раздел 1.4, 11.5) |

**Легенда статусов:** ✅ готово · 🟡 частично · ⬜ не реализовано (запланировано) · ❌ не портируем / вне области.

**Регламент:** каждый спринт обязан пополнять журнал по затронутым API.

### 10.1. Документация-зеркало как система самопроверки

`API_PARITY.md` — это таблица; дополняем её **зеркальной документацией**, которая делает паритет видимым и проверяемым, а не учётным. Принцип: **на каждую страницу официальной документации ManimCE — наша параллельная страница.** Это не документация ради документации, а измерительный прибор: объём наполнения API и объём реально портированного функционала становятся видны напрямую, страница к странице.

**Архитектура веб-зеркала (`docs/`)** строится на четырёх главных несущих столпах, воспроизводящих официальный портал Manim Community:

1. **Галерея примеров (`examples.html` — исполняемая спецификация):**
   Полный порт **реальной** канонической галереи сцен ManimCE (4 секции, 19 сцен; *сверено по ManimCE v0.20.1 — в ходе разработки перепроверить, состав галереи зависит от версии*, паттерн D-14):
   - *Basic Concepts:* `ManimCELogo`, `BraceAnnotation`, `VectorArrow`, `GradientImageFromArray`, `BooleanOperations`;
   - *Animations:* `PointMovingOnShapes`, `MovingAround`, `MovingAngle`, `MovingDots`, `MovingGroupToDestination`, `MovingFrameBox`, `RotationUpdater`, `PointWithTrace`;
   - *Plotting with Manim:* `SinAndCosFunctionPlot`, `ArgMinExample`, `GraphAreaPlot`, `PolygonOnAxes`, `HeatDiagramPlot`;
   - *Special Camera Settings:* `FollowingGraphCamera`.

   Каждая сцена воспроизводится на нашем Kotlin-DSL, и рядом с кодом отображается автоматически сгенерированная в CI эталонная GIF/APNG анимация. Галерея служит главным визуальным доказательством выразительности движка. Поскольку галерея объявлена исполняемой спецификацией паритета, её состав ведётся **перечислимой таблицей «сцена → статус»** в `API_PARITY.md` (а не свободным текстом). *Примечание:* `SquareToCircle`/`OpeningManim` — это сцены туториала Quickstart (столп 2), а `Wiggle`/`LaggedStartMap` — классы Reference Manual (столп 3), а **не** сцены галереи.
2. **Индекс туториалов и гайдов (`tutorials/index.html` — обучающий хаб):**
   Воспроизводит образовательную линейку ManimCE, **сохраняя её реальное деление на два верхнеуровневых раздела** (Tutorials и Thematic Guides):
   - `tutorials/` (**Tutorials**):
     - `quickstart.html` (Быстрый старт: установка, первая Activity и запуск KManim; здесь же quickstart-сцены `SquareToCircle` и т. п.)
     - `output_and_config.html` (Output Settings — *в v0.16 был пропущен, добавлен*)
     - `building_blocks.html` (Строительные блоки сцен: MObjects, VMobjects, VGroups)
   - `guides/` (**Thematic Guides**):
     - `configuration.html` (Настройка RenderContext, RenderThread и SurfaceView)
     - `deep_dive.html` (Глубокое погружение: кадровый цикл, временной детерминизм и rate-функции)
     - `using_text.html` (Rendering Text and Formulas: TextLabel и контурный VectorText с KaTeX-формулами — имя файла совпадает с реальным URL ManimCE)
     - `add_voiceovers.html` (Adding Voiceovers — статус ❌, видеоозвучка вне области, ср. 1.4/11.5)
3. **Справочник API (`reference.html` — точный измерительный прибор):**
   Полный справочник, **раздел в раздел, класс в класс**, со строгими визуальными маркерами статуса (✅ / 🟡 / ⬜ / ❌) у каждой сущности. Если у ManimCE есть страница про класс, а у нас её нет или она ⬜ — разрыв виден мгновенно.
4. **Интерактивные медиа-иллюстрации из CI:**
   Все GIF и APNG генерируются исключительно реальным Skia/Filament-рендером Android-приложения в CI через golden-харнесс с ручным временным детерминизмом (раздел 8.1). Опционально встраивается Kotlin Playground для интерактивного редактирования синтаксиса DSL.

**Воспроизведённые примеры как эшелон тестов («manim-parity examples»).** Канонические сцены из `examples.html` (`BraceAnnotation`, `BooleanOperations`, `VectorArrow` и т. д. — см. реальный перечень в столпе 1) реализуются на нашем DSL и прогоняются через golden-харнесс (раздел 8). Это превращает галерею примеров в **исполняемую спецификацию паритета**: не «мы реализовали `Transform`», а «мы воспроизвели манимовский пример, и вот совпадающая картинка». Эшелон встаёт рядом с обычными golden-тестами.

**Картинки и гифки — из настоящего рендера, не из веб-движка.** Иллюстрации для зеркальной документации генерирует само Android-приложение в CI: golden-харнесс и так рисует кадры в `Bitmap` на эмуляторе — последовательность кадров склеивается в GIF/APNG. Это честные артефакты нашего Skia-рендера, без отдельной веб-реализации (полноценный веб-рендеринг отклонён, раздел 4.8). Опционально на страницах можно встроить Kotlin Playground для показа и редактирования DSL-синтаксиса (компиляция без рендера), рядом — готовая гифка результата.

**Задача `generateMirrorDocs` (спецификация, D-45).** Генератор `docs/` — Gradle-задача в `build-logic` (Kotlin, **без Node**; Node нужен лишь для compile-time KaTeX со Спринта 5). Источник данных — `API_PARITY.md` плюс статический реестр страниц/классов ManimCE; HTML собирается самописным Kotlin-генератором (`kotlinx.html` либо строковые шаблоны). Склейку PNG-срезов (8.1) в GIF/APNG выполняет **чисто-JVM энкодер** (без нативного ffmpeg — запрет FFmpeg по D-11 касается только рантайм-видеоэкспорта `.mp4`, а не CI-инструментов; версия — в `libs.versions.toml`, 7.1), запускаемый внутри той же задачи **после** golden-харнесса. Тайминг: в Спринте 0 задача генерирует каркас `docs/` с плейсхолдерами (golden рисует лишь «чёрный квадрат») и завершается успехом; реальная склейка медиа подключается со Спринта 1 (первый анимированный пример). `generateMirrorDocs` входит в обязательную pre-commit команду 15.6.

**Регламент:** при добавлении/изменении публичного API спринт обновляет и `API_PARITY.md`, и соответствующую зеркальную страницу; для затронутых канонических примеров добавляется/обновляется golden-тест «manim-parity».

> [!IMPORTANT]
> **Инвариант 100% учётного паритета при 70–80% кодовой реализации**
> ИИ-агентам и разработчикам критически важно понимать: в HTML-зеркале (особенно в `reference.html`) должна присутствовать **100% опись всех классов, страниц и методов ManimCE**. При приёмке проверяется именно 100% наличие структурных страниц. Однако по кодовой реализации это будет реалистичный потолок ~70–80% (раздел 11.5). Сущности, не портируемые в реальном времени (например, экспорт видео в `.mp4`), обязаны присутствовать в справочнике с явным статусом ❌ или 🟡.

## 11. План расширения (Roadmap за горизонтом основного плана)

Архитектура (раздел 5) спроектирована так, чтобы всё нижеперечисленное подключалось **как новые реализации существующих интерфейсов**, без переписывания ядра.

### 11.1. 3D-рендеринг
Через `Renderer3D`. Первичный бэкенд — Filament. См. Спринт 7.

### 11.2. Vulkan
Подключается как ещё одна реализация `Renderer3D` (либо напрямую, либо «под капотом» Filament). Условия безболезненности — раздел 5.5.4. Реализуется только при обоснованной необходимости (профайлинг покажет узкое место) или под compute-задачи (векторные поля, симуляции частиц, параметрические поверхности с тысячами точек).

### 11.3. Android XR / OpenXR
Подключается как ещё одна реализация интерфейса рендеринга/представления. Главное условие — соблюдение инварианта 5.1 (ядро и DSL не знают про бэкенд). Максимальная модальность и абстракции — сознательная стратегическая цель проекта именно ради этого направления.

### 11.4. Расширение сообществом
Модульная структура (раздел 6) позволяет добавлять библиотеки объектов отдельными модулями/плагинами по образцу экосистемы ManimCE.

### 11.5. Принципиальные ограничения (что в категорию ❌)
Чистым Kotlin недостижимы **некоторые** возможности Manim, потому что они *определены через* Python-экосистему или выходят за рамки реального времени:
- Полный пайплайн LaTeX → dvi → SVG (JLaTeXMath покрывает значимую, но не всю часть).
- Вся обширная встроенная библиотека готовых объектов Manim (годы наработок; добавляем по мере надобности).
- Сложные SVG-манипуляции и продвинутые шейдерные эффекты последних видео 3b1b.
- Видеоэкспорт как определяющий режим (см. раздел 1.4).

Поэтому реалистичный потолок паритета — ~70–80% Manim; но это не цель проекта (раздел 1.5).

### 11.6. Иные платформы (десктоп, веб) через шов
Десктоп, веб и прочие таргеты — вне области первой версии (фокус на Android, D-1), но достижимы **как порт адаптеров, а не разворот в мультиплатформу** (D-25, D-26). Переносимое ядро (DSL, объекты, анимации, геометрия, тайминг) — чистый Kotlin; платформенным остаётся только нижний слой за швом: новая реализация `Renderer2D` (на десктопе/вебе — Skiko/Canvas-web), своя поверхность и потоковая модель, для 3D — десктопные биндинги Filament. Веб дополнительно ограничен отсутствием нативных Android API и не покрывает 3D. Это работа для отдельного плагина/форка силами сообщества, по образцу того, как отклонён видеоэкспорт (11.4) — ядро при этом не трогается.

Сейчас отклонено осознанно (D-10): целевой перф 60 FPS не для бюджетных старых GPU, а каждый шаг вниз по API расширяет матрицу тестов и платформозависимые баги. Пересмотреть, когда ядро стабильно.
- **O-7.** *(0.9; уточнён в 0.17.)* Поддержка **динамических формул** (структура формулы меняется в рантайме, строка неизвестна на сборке) — на потом. Основной путь LaTeX — compile-time раскладка (D-20), рантаймовый JS-движок добавляется как опциональная реализация `TexEngine` без правок ядра (D-27), когда/если такой сценарий понадобится. Решить, нужен ли он в v1 (по умолчанию — нет). *Уточнение:* модель «один движок на приложение, выбор в фабрике» не покрывает приложение, **смешивающее** литеральные и динамические формулы (`AssetTexEngine` не отдаст путь для рантайм-неизвестной строки, а прогон всех литералов через рантайм-движок ломает выгоду compile-time D-20). Для такого случая нужна пер-вызовная маршрутизация (литерал → ассет, динамика → рантайм) — её специфицировать вместе с решением по O-7.

Вычисления и отрисовка вынесены с UI-потока на выделенный `RenderThread` (см. D-22). Контракт `Scene` интегрирован с жизненным циклом Android. (Раздел 5.4, Приложение B.)
- **D-18.** *(Аудит 0.5, дополнено 0.6, пересмотрено 0.8.)* В `ThreeDScene` 2D-оверлеи рендерятся через offscreen-текстуру (Canvas → Filament-материал на quad), а не через несуществующий GPU-векторный рендерер. Честный 3D-интерливинг 2D-фигур в v1 не поддерживается сознательно. Против давления на шину памяти — мелкие билборды (статичное заливается один раз, перезаливается только анимируемое). Обновление текстур — через **пул `Bitmap` фиксированных размеров + `Texture.setImage`** (Filament копирует переданный `PixelBufferDescriptor`, поэтому `Bitmap` из пула безопасно перерисовывать; против in-flight-сэмплирования — ping-pong из двух текстур на слот, D-37), а не zero-copy `AHardwareBuffer` с sync-fences: барьерная синхронизация Skia→Filament платформозависима и хрупка (Adreno/Mali), а пул даёт <0.2 мс и безопасность по потокам. `AHardwareBuffer` — возможная оптимизация на потом. (Разделы 4.6, 5.7, Спринт 7.)
- **D-19.** *(Аудит 0.5.)* Текст разделён на `TextLabel` (растровый, `StaticLayout`) и `VectorText` (контурный, `Paint.getTextPath` → `VectorPath`). `Create`/`Transform` применимы только к `VectorText`. (Разделы 5.2, 6, Спринт 4.)
- **D-20.** *(Аудит 0.5; пересмотрено 0.6 и 0.9.)* Движок формул — **KaTeX** (не JLaTeXMath, у которого фатальная зависимость от отсутствующего в Android AWT). Основной путь — **compile-time раскладка**: Gradle-плагин на сборке прогоняет формулы-литералы через KaTeX под Node, парсит SVG-пути в `VectorPath` и кладёт в ассеты APK; в рантайме формула не парсится, JS-движок в APK не входит, если нет динамических формул. (Раздел 5.8, Спринт 5.)
- **D-21.** *(Аудит 0.5, дополнено 0.6, уточнено 0.8 и 0.17.)* Golden-тесты в два эшелона: Robolectric на JVM для скорости (на каждый коммит) + androidx.test на устройстве/эмуляторе как пиксельный эталон. Robolectric не гарантирует пиксельного совпадения со Skia, поэтому эталоном не считается; точность проверяется в Спринте 0. Против flaky: **единый инструмент Roborazzi** (быстрый эшелон на JVM; эталонный — on-device режим, D-46) с порогом совпадения **≥98%**, перцептивное сравнение (SSIM/доля различающихся пикселей), эталон только на фиксированной конфигурации **`Pixel 6 Pro / API 34 / x86_64`** (прогон эталонов на несоответствующих машинах запрещён); к фиксируемым факторам эталона добавлена версия ассетов формул (KaTeX/шрифты, D-41). (Раздел 8, 7.1.)
- **D-22.** *(Аудит 0.6.)* Архитектура игрового движка: вычисления сцены и отрисовка — на выделенном `RenderThread` поверх `SurfaceView` (`lockHardwareCanvas`/`unlockCanvasAndPost`); UI-поток только принимает ввод в потокобезопасную очередь. Защищает от jank и блокировки касаний, которую дал бы `Choreographer` на UI-потоке. (Раздел 5.4.)
- **D-23.** *(Аудит 0.6, пересмотрено 0.8.)* Геометрия — **двухуровневая** (раздел 5.2.1): объектный `TopologicalPath` (холодный путь — сопоставление контуров, реверс обхода, подразбиение) компилируется в плоский `FlatVectorPath` (`FloatArray`, горячий путь — покадровая интерполяция, zero-alloc) только при изменении формы (dirty-флаг). Интерполяция в горячем пути — строго между двумя скомпилированными `FlatVectorPath`; компиляция из топологии в горячем пути запрещена. Снимает противоречие «удобство математики ↔ скорость без GC» и риск Спринта 3. (Разделы 5.2, 5.2.1, 5.9, Приложение A/B.)
- **D-24.** *(Аудит 0.6; уточнено 0.17.)* В морфинге (`Transform`) даже для простых контуров обязательны проверка направления обхода (реверс при несовпадении) и рост недостающих подпутей из центроидов. Сопоставление точек — `VMobject.matchPoints(other)` как **метод объекта** (паритет с `Mobject.match_points`, на холодном `TopologicalPath`), а сопоставление **частей** при сложных переходах — отдельные классы анимаций `TransformMatchingShapes`/`TransformMatchingTex`, **а не** билдер `Transform(...).matchPoints(...)` (он исказил бы семантику одноимённого метода ManimCE). Сложные топологии — вне v1. (Спринт 3, 5.8.)
- **D-25.** *(0.7.)* Документация-зеркало как система самопроверки: на каждую страницу manim-доков — наша параллельная, особенно детально для `reference.html` (раздел в раздел, со статусом); канонические примеры из `examples.html` воспроизводятся на нашем DSL и становятся golden-эшелоном «manim-parity»; иллюстрации-гифки генерирует Android-приложение в CI (не веб-движок). (Раздел 10.1.)
- **D-26.** *(0.7.)* Переносимость — через шов, а не через мультиплатформу. Десктоп/веб/иные таргеты достижимы как порт адаптеров (`Renderer2D`/`Renderer3D`, поверхность, потоки), ядро не трогается; это плагин/форк вне области v1. Полноценный веб-рендеринг и KMP/Skiko как путь ядра отклонены (раздел 4.8). Герметичность шва (инвариант 5.1) — условие переносимости. (Разделы 4.8, 11.6.)
- **D-27.** *(Аудит 0.8; переформулировано 0.9.)* Рантаймовый JS-движок (QuickJS+KaTeX) — **опциональный fallback только для динамических формул**. В этом режиме против фриза холодного старта: асинхронный прогрев на старте (`Application.onCreate`), дисковый кэш `VectorPath` по строке, парсинг один раз (анимация над готовой геометрией). Для статических формул (основной путь, D-20) рантаймовый JS не нужен. (Раздел 5.8, Спринт 5.)
- **D-28.** *(0.10.)* Основной 3D-бэкенд — **Filament** (а не libGDX/сырой OpenGL ES). Причины: специализированный PBR-рендер, а не широкий игровой фреймворк (нам не нужны его ввод/аудио/сцены/game loop — всё это у нас своё); мобильная заточенность от Google (память, энергопотребление, троттлинг); инкапсулирует Vulkan/GL ES и служит мостом к Vulkan/XR через `Renderer3D` (D-7); модель интеграции «меш+камера → кадр» на нашу `Surface` без захвата цикла приложения. libGDX проще на старте и кроссплатформен, но кроссплатформенность нам не нужна (D-1), а его game loop конфликтует с нашим `RenderThread` (D-22). Закрывает O-3. **Оговорка:** подтвердить совместную работу Filament с `SurfaceView`/потоковой моделью и перезаливкой текстур билбордов экспериментом на железе (проверки Спринта 0, реализация — Спринт 7). (Разделы 5.7, 7, Спринт 7.)
- **D-29.** *(0.11.)* Источник истины состояния разработки — **репозиторий (git)**, не контекст агента и не одна машина. Всё (ТЗ, `STATUS.md`, `DEVLOG.md`, `API_PARITY.md`, зеркальная документация, код) хранится в репе и читается с нуля. Сведения вне репозитория считаются эфемерными/потерянными. (Раздел 14.1.)

Использование реального времени или `Thread.sleep()` в golden-тестах запрещено. Гарантирует отсутствие flaky-тестов и автоматическую сборку GIF/APNG для веб-документации `docs/`. (Разделы 8.1, 15.1.)

(Раздел 10.1.)

В сигнатурах, конструкторах и тестах используется конкретный тип. Исправлена самопротиворечивая сигнатура `TexEngine` (теперь `String → TopologicalPath` везде) и некомпилируемый `VectorPath(FloatArray(0))` в Приложении B (→ `FlatVectorPath`). (Глоссарий, 5.2.1, 5.5.1, 5.8, Приложения A/B.)
- **D-35.** *(0.17.)* **Единый контракт `Animation`.** Базовый `interpolate(alpha)` мутирует `MObject` (Fade/Shift/Scale/Rotate); контуро-порождающие реализуют маркер `PathAnimation.interpolatePath(alpha, out: FlatVectorPath)` (zero-alloc). Публичное поле — `duration: Float` (секунды), каноничная внутренняя единица — наносекунды (`durationNanos`, конвертация один раз в `Scene`). `rateFunc: RateFunction` (именованный `fun interface`). Имя линеаризации — `toFlat()` (холодный путь, аллокация допустима). Контракт `Animation` добавлен в Приложение A. (5.2.1, 5.3, 5.9, Приложения A/B.)
- **D-36.** *(0.17.)* **Стратегия мелких мат-типов.** `Vector2`/`Matrix`/`Mat3`/`Mat4`/`Transform` — обычные mutable дата-классы, переиспользуемые через пул и/или `out`-параметр (мультиполевой `value class` нестабилен на Kotlin 2.0); `value class` — только однополевой `Color` (ARGB `Int`), и не в дженериках/nullable/коллекциях. Источник zero-alloc — `FloatArray`-хранение (D-23) и пулы/out-параметры, а не value-семантика. Убрана неверная гарантия «value class ⇒ без боксинга» и противоречие «`Vector2` одновременно value class и из пула». (4.9 п.3, 5.9 п.3, Приложение A.)
- **D-37.** *(0.17.)* **Кадровый такт и обновление текстур.** Источник такта — VSYNC через `Choreographer.frameTimeNanos`; блокировка `dequeueBuffer` внутри `lockHardwareCanvas()` — back-pressure `BufferQueue` (страховка от забегания продьюсера), **а не** «VSYNC-троттлинг»/основной пейсинг. `Texture.setImage` сам по себе двойную буферизацию не даёт — безопасность даёт copy `PixelBufferDescriptor`; против in-flight-сэмплирования анимируемых билбордов — ping-pong из двух текстур (подтвердить device-spike, D-28). (5.4, 5.7, Приложение B, D-18.)
- **D-38.** *(0.17.)* **2D-камера.** Введена backend-нейтральная `SceneFrame`/`Camera2D` в `manim-core` (manim-юниты, дефолт 14.222×8.0 при 16:9), которой владеет `Scene`. `Scene` вычисляет вьюпорт-`Mat3` (сцена→пиксели, letterbox) и передаёт в `Renderer2D` итог `viewport ∘ objectTransform` — порт остаётся вьюпорт-агностичным. `Camera(Mat4)` — только 3D. Обратное преобразование экран→сцена — для хит-тестинга. `MoveCamera`/zoom — анимации над `SceneFrame`. (5.5.1, 5.5.6, Спринт 1, Приложение A, глоссарий.)
- **D-39.** *(0.17.)* **`VGroup`.** Тонкая группа поверх дерева `submobjects`: без собственной геометрии (`draw` пуст), трансформа наследуется детьми; dirty-флаг агрегированных границ при изменении состава; не дублирует `submobjects`. Матричный инвариант (накопление матриц) — то, что проверяют property-тесты Спринта 2. Сахар (`+=`/индексация/`arrange()`) — в `*Ext.kt`. (Глоссарий, 5.2, Приложение A, Спринт 2.)
- **D-40.** *(0.17.)* **Жизненный цикл ресурсов.** Инвариант «один `upload` ↔ один `release`; каждый `Bitmap` из пула → `recycle()`». У `MObject` — `onDetach(ctx)` (рекурсивный по `submobjects`, вне горячего пути), вызывается `Scene` при удалении объекта и при `surfaceDestroyed` (иначе `MeshHandle`/`TextureHandle` утекают при пересоздании `Surface`). Кэш геометрии формул — со временем жизни объекта, сброс в `onDetach`. (5.4, 5.5.7, 5.7, Приложение A.)
- **D-41.** *(0.17.)* **Ассеты формул и ошибки `TexEngine`.** Ключ ассета = стабильный хэш кортежа (нормализованная строка, версия KaTeX, версия шрифтов, версия SVG-парсера/формата); рантайм-кэш (D-27) — тот же ключ; Gradle-таск cacheable. Обнаружение литералов `mathTex("…")` — через KSP/компиляторный плагин; всё динамическое → рантайм-fallback (O-7) либо детерминированная ошибка сборки. SVG-парсер: команды M/L/C/S/Z, неподдержанные (Q/T/A/относительные) — нормализуются в кубические Безье на сборке либо ошибка сборки (не молчаливый пропуск). ### Приложение B. Сцена и модель времени на выделенном RenderThread (концептуально)

> **Важно:** это НЕ блокирующий `while` на UI-потоке (ANR) и НЕ работа в колбэке `Choreographer` на UI-потоке (jank + блокировка касаний). Вычисления и отрисовка идут на отдельном `RenderThread` поверх `SurfaceView`; шаг — по дельте реального времени. UI-поток только кладёт ввод в потокобезопасную очередь. См. раздел 5.4 (решения D-17, D-22). Цикл спроектирован аллокационно-чистым (5.9): без лямбд и боксинга на кадр.

```kotlin
fun scene(build: Scene.() -> Unit): Scene = Scene().apply(build)

class Scene {
    private val mobjects = ArrayList<MObject>()
    private val queue = ConcurrentLinkedQueue<Animation>()   // потокобезопасный обмен с UI
    private val outPath = FlatVectorPath(FloatArray(0))      // предвыделенный плоский горячий контейнер (zero-alloc); НЕ зонтичный VectorPath (D-34)
    private var current: Animation? = null
    private var elapsedNanos = 0L

    // Вызывается с UI-потока; не блокирует — только кладёт в очередь.
    fun play(vararg anims: Animation) { for (a in anims) queue.add(a) }

    // Один шаг кадра. Вызывается с RenderThread; dtNanos — дельта между соседними frameTimeNanos
    // из Choreographer.postFrameCallback (источник такта, D-37), а НЕ время возврата из lockHardwareCanvas.
    fun stepFrame(dtNanos: Long, r: RenderContext) {
        var anim = current
        if (anim == null) { anim = queue.poll()?.also { current = it; elapsedNanos = 0L } }
        if (anim != null) {
            elapsedNanos += dtNanos
            val alpha = (elapsedNanos.toFloat() / anim.durationNanos).coerceIn(0f, 1f)
            val eased = anim.rateFunc(alpha)                  // RateFunction.invoke (SAM)
            anim.interpolate(eased)                           // базовая форма: мутирует target (Fade/Shift/Scale/Rotate)
            if (anim is PathAnimation) anim.interpolatePath(eased, outPath)  // контуро-порождающие → zero-alloc в outPath
            if (alpha >= 1f) current = null
        }
        for (i in mobjects.indices) mobjects[i].draw(r)        // обход без лямбд
    }
}

// RenderThread (упрощённо): такт — от Choreographer.frameTimeNanos (D-37); захватывает канвас
// SurfaceView из фонового потока и постит кадр через unlockCanvasAndPost() (back-pressure BufferQueue
// здесь — лишь страховка, не источник пейсинга); время берёт из дельты frameTimeNanos.
// class RenderThread(holder: SurfaceHolder, scene: Scene) : Thread { ... }
```

### Приложение D. Каталог rate-функций (паритет с ManimCE)

**Сверено по ManimCE v0.20.1** (файл `manim/utils/rate_functions.py`, ветка `main`). Набор стабилен с v0.19.1. **В ходе разработки перепроверить по актуальной версии ManimCE** — список мог пополниться (D-14). Подробные формулы, сигнатуры и значения параметров по умолчанию — в отдельном сверочном отчёте по rate-функциям.

Контракт типа: `fun interface RateFunction { fun invoke(t: Float): Float }` (аналог `(Float) -> Float`; совместим с `Interpolator.getInterpolation(...)` из Android — см. 4.7).

**Именование (D-43).** Имена rate-функций сохраняются в оригинальном snake_case ManimCE (`there_and_back_with_pause`, `ease_in_out_bounce`, `squish_rate_func`, декораторы `unit_interval`/`zero`, параметры `pause_ratio`/`pull_factor`/`half_life`) — осознанное исключение из Kotlin-конвенции ради буквального паритета имён (D-3, D-14). Доступ — через namespace-объект `RateFunctions` (например `RateFunctions.there_and_back`). Чтобы линтер (15.6) не блокировал коммит, правила detekt `FunctionNaming`/`VariableNaming`/`ConstructorParameterNaming` подавляются **scoped** — только для файла/пакета rate-функций через baseline, а не глобально.

**В `__all__` модуля (17)** — базовые и часто используемые:
`linear`, `smooth`, `smoothstep`, `smootherstep`, `smoothererstep`, `rush_into`, `rush_from`, `slow_into`, `double_smooth`, `there_and_back`, `there_and_back_with_pause`, `running_start`, `not_quite_there`, `wiggle`, `squish_rate_func`, `lingering`, `exponential_decay`.

**Стандартные ease-функции (30)** — 10 семейств × 3 варианта (`ease_in_*`, `ease_out_*`, `ease_in_out_*`):
`sine`, `quad`, `cubic`, `quart`, `quint`, `expo`, `circ`, `back`, `elastic`, `bounce`.
Все 30 — публичная часть API ManimCE и входят в целевой набор (раздел 5.3, D-14); они просто не включены в `__all__` модуля. Метка `__all__` выше — про членство в `__all__`, а не про (не)доступность.

**Служебные декораторы:** `unit_interval`, `zero` (клиппинг выхода в `[0,1]` либо в 0 вне интервала).

**Оговорки для переноса:** `not_quite_there` и `squish_rate_func` возвращают функцию-обёртку, а не число — у нас это функции высшего порядка над `RateFunction`. Значения параметров по умолчанию сохранить как в оригинале — **с явным маппингом «функция → параметры»** (плоский список прежних версий ошибочно приписывал `inflection=10.0` функции `not_quite_there`, у которой на деле `proportion=0.7`):

| Функция | Параметры по умолчанию |
|---------|------------------------|
| `smooth`, `there_and_back`, `rush_into`, `rush_from` | `inflection=10.0` |
| `there_and_back_with_pause` | `pause_ratio=1/3` (≈0.333) |
| `running_start` | `pull_factor=-0.5` |
| `not_quite_there` | `func=smooth`, `proportion=0.7` |
| `wiggle` | `wiggles=2` |
| `exponential_decay` | `half_life=0.1` |
| `squish_rate_func` | `a=0.4`, `b=0.6` |

Ту же таблицу обязательно завести (или сослаться на неё) в отдельном сверочном отчёте по rate-функциям, чтобы значения не разошлись по двум местам. До полной сверки кривых такие функции держим в `API_PARITY.md` как 🟡.

## 14. Процесс разработки и мониторинг состояния

Цель раздела — чтобы **любой** (разработчик-человек, ИИ-агент, внешний контрибьютор) в любой момент мог понять состояние разработки, что активно сейчас, и продолжить с текущего или указанного места — после сбоя агента, смены агента/машины или паузы хоть в год.

### 14.1. Принцип: источник истины — репозиторий (D-29)

Состояние разработки живёт **в git, а не в голове агента и не в его контекстном окне**. Контекст ИИ эфемерен (обнуляется при сбое, смене модели, новой машине), а человек забывает за год — поэтому всё, что нужно для восстановления, хранится файлами в репозитории и читается с нуля. В репозитории лежит **всё**: настоящее ТЗ, `STATUS.md`, `DEVLOG.md`, `API_PARITY.md`, зеркальная документация (10.1) и код. Ничто из состояния проекта не существует вне репозитория. Если сведение живёт только в переписке, в памяти агента или на одной машине — оно считается потерянным.

### 14.2. Три слоя состояния (разная частота изменения)

Состояние разнесено по трём артефактам намеренно — у них разные вопросы и разный режим порчи; смешивать их нельзя (история раздула бы снимок настоящего, а перезапись затёрла бы историю):

**1. `STATUS.md` — снимок настоящего (перезаписывается).** Маленький файл, всегда отражает текущий момент; первое, что читают на входе в проект. Содержит: активный спринт; конкретную задачу в работе; что уже зелёное; следующий шаг; раздел **«Как продолжить»** (какие команды запустить, где именно остановились); ссылку на последний значимый коммит. Не растёт — перезаписывается. Отвечает на «что происходит **прямо сейчас**».

> - [ ] golden-тесты «manim-parity» для затронутых канонических примеров (10.1)
> - [ ] Обновлена таблица `API_PARITY.md`
> - [ ] Обновлены `STATUS.md` и `DEVLOG.md`; зеркальная HTML-страница в `docs/` со встроенной GIF/APNG готова
> - [ ] Коммит и тег `sprint-N-done` **запушены на origin** (D-48)

**2. `DEVLOG.md` — хронология прошлого (append-only).** Лента истории; **только дописывается, никогда не перезаписывается и не теряется**. Одна запись **на рабочую сессию** (вошёл-вышел) по строгому машиночитаемому шаблону. Отвечает на «как мы сюда пришли» и «почему вот это сделано именно так».

Шаблон записи:
```
## [YYYY-MM-DD] Сессия N — Спринт M
- Сделано: <что конкретно завершено/изменено>
- Решения: <принятые по ходу решения и КОРОТКО почему; для крупных — ссылка на D-XX в ТЗ>
- Грабли: <на что наткнулись, что не сработало — чтобы не повторять>
- Следующий шаг: <с чего начинать следующую сессию>
- Якорь: <полный хеш HEAD сессии (`git rev-parse HEAD`) и/или тег `session-N`>, запушен на origin
```

Поле «Якорь» — head сессии (полный хеш и/или аннотированный тег), **запушенный на origin**; промежуточные **атомарные** коммиты (15.4) находятся диапазоном `git log <якорь_прошлой_сессии>..HEAD`. Запрещён ручной 7-символьный префикс хеша — он хрупок к rebase/clone (именно так возникли фантомные хеши, устранённые в 0.17, D-48).

**3. Журнал решений в ТЗ (раздел 12.2, серия D-N — D-1 и далее) — уже есть.** Крупные архитектурные развилки идут сюда (с обоснованием), мелкие реализационные — в `DEVLOG.md`. Не дублируем: DEVLOG ссылается на D-XX.

### 14.3. Привязка к коду

Чтобы файлы состояния не разошлись с реальным кодом: `STATUS.md` держит ссылку на последний значимый коммит (полный хеш и/или тег); сообщения коммитов привязываются к спринту/задаче; на завершение каждого спринта ставится аннотированный **git-тег** `sprint-N-done` (`sprint-0-done`, `sprint-1-done`, …) — точки навигации по истории. **Коммиты и теги обязательно пушатся на origin** (D-29/D-48: локальное без push считается потерянным), иначе на другой машине якоря не видно. Перед закрытием спринта якорь проверяется машинно: `git cat-file -e <хеш из STATUS.md>` должен проходить, а `git tag -l 'sprint-*'` для завершённых спринтов — быть непустым. Тогда «где остановились» восстанавливается двусторонне: из `STATUS.md` → в код и из git-истории/тегов → обратно.

### 14.4. Ритуал сессии (D-30) — что делает систему живой

Без обязательного ритуала файлы протухают, поэтому правило жёсткое (фиксируется в Спринте 0 и входит в Definition of Done каждого спринта):

- **На входе** в сессию (любой агент/человек) — единый входной ритуал: прочитать `STATUS.md` → нужный хвост `DEVLOG.md` (**включая поле «Грабли»**) → `API_PARITY.md` → при необходимости релевантные разделы ТЗ и интерфейсы `manim-core`. Затем сверить «последний значимый коммит» из `STATUS.md` с git HEAD: при расхождении считать прошлую сессию аварийно прерванной и сначала восстановить/пометить состояние, а не продолжать вслепую.
- **На выходе** из сессии: обновить `STATUS.md` (новый снимок настоящего + «как продолжить») и дописать запись в `DEVLOG.md` по шаблону; закоммитить **и запушить** (`git push`); на границе спринта — поставить **и запушить** тег (`git push origin sprint-N-done`).
- **Аварийный/незавершённый выход** (остановка по 15.2 или любое прерывание): дописать в `STATUS.md` «Задачу в работе» с пометкой «⚠ НЕЗАВЕРШЕНО: <что делалось, на чём остановились, причина>» и «как продолжить»; сделать коммит **только md-файлов состояния** (`STATUS.md` + запись в `DEVLOG.md` с пометкой «сессия прервана»), даже если код не в зелёном состоянии — это разрешённое исключение из терминальной верификации 15.6; запушить.

Тогда все сценарии — «агент упал и восстановился», «сменили агента», «другая машина», «вернулся через год» — это **один и тот же** путь: пройти входной ритуал (`STATUS.md` → `DEVLOG.md` → `API_PARITY.md`) → продолжить.

## 15. Протокол автономной работы ИИ-агентов (AI Guidelines)

Этот раздел содержит **обязательные** правила поведения для любых ИИ-ассистентов, работающих с кодовой базой KManim. Нарушение этих правил ведет к деградации архитектуры.

### 15.1. Ограничение самодеятельности (Strict API Parity)
- **Ядро 1-к-1 с ManimCE:** При реализации математики, логики сцен, фигур (`MObject`) и анимаций, агент **обязан** зеркалировать публичные методы оригинального Python ManimCE. Запрещено выдумывать собственные методы ради "удобства".
- **Изоляция Kotlin-сахара:** Любые улучшения DSL, специфичные для Kotlin (infix-функции, builders вроде `circle { ... }`), **должны** выноситься в отдельные файлы расширений (например, `*Ext.kt`). Это сохраняет ядро чистым портом.
- **Имена rate-функций — snake_case (D-43):** каталог rate-функций именуется как в ManimCE (`there_and_back_with_pause`, `ease_in_out_bounce` и т. д.) через namespace-объект `RateFunctions` — осознанное исключение из Kotlin-конвенции ради буквального паритета; правила detekt подавляются **scoped** (только пакет rate-функций, не глобально), чтобы 15.6 не блокировал коммит.
- **Временной детерминизм тестов:** При написании golden-тестов для любых time-dependent API (анимации, апдейтеры, `.animate`) ИИ-агент обязан применять дискретное ручное сэмплирование временных шагов (раздел 8.1). Использование реального времени, потоков или `Thread.sleep()` строго запрещено.

### 15.2. Алгоритм отладки ("Стоп и Анализ")
- **Запрет на костыли:** Категорически запрещено рефакторить интерфейсы ядра (`manim-core`) для починки локального теста. Если ошибка кроется в архитектуре ядра, агент обязан остановиться, зафиксировать проблему **по процедуре аварийного выхода (14.4)** (`STATUS.md` с пометкой «⚠ НЕЗАВЕРШЕНО» + запись в `DEVLOG.md` + коммит состояния, запушенные на origin) и запросить помощь человека.

### 15.3. Обязательный ритуал контекста (Context Ritual)
ИИ работает вслепую без контекста. Перед написанием первой строчки кода агент **обязан**:
1. Пройти единый входной ритуал контекста по разделу 14.4 (D-30): `STATUS.md` → хвост `DEVLOG.md` (**включая «Грабли»** — иначе риск повторить уже известную ошибку) → `API_PARITY.md`.
2. Изучить существующие интерфейсы в `manim-core`, относящиеся к задаче.

### 15.4. Атомарные коммиты
- Агент должен фиксировать работу мелкими, логически завершенными порциями (1 логический блок = 1 коммит).
- Запрещено вываливать результаты долгой генерации десятков файлов в один огромный коммит.
- В `DEVLOG.md`/`STATUS.md` фиксируется head сессии (полный хеш и/или тег, запушенный на origin); адресность промежуточных атомарных коммитов обеспечивает git-история диапазоном `git log <якорь_прошлой_сессии>..HEAD` (14.2), отдельно их перечислять не нужно.

### 15.5. Чистая Git-история (No AI Traces)
- **Запрет на упоминание ИИ:** В сообщениях коммитов категорически запрещено указывать, что код сгенерирован ИИ (никаких префиксов "[AI]", "Generated by assistant" и т.д.).
- Агенты обязаны использовать локальный или глобальный `git config` машины пользователя (с его именем и email) и писать обычные, лаконичные описания коммитов от первого лица.

### 15.6. Обязательная терминальная верификация (Pre-Commit Verification)
Перед формированием коммита и обновлением `STATUS.md` агент **обязан** запустить полную проверку сборки, локальных тестов и генерации документации единой командой:
```bash
./gradlew check assembleDebug generateMirrorDocs
```
Комит допускается только при 100% успешном прохождении линтинга, JVM unit-тестов, скриншот-тестов Roborazzi (быстрый JVM-эшелон), успешной сборке APK и **успешной генерации HTML-зеркала документации**.

**Уровень команды (D-47).** Эта команда покрывает только **per-commit**-уровень верификации; она НЕ запускает инструментальные device-тесты (`check` ≠ `connectedCheck`). Полный Definition of Done спринта (эталонный on-device golden + golden «manim-parity») определяется чек-листом 14.2 и закрывается перед установкой тега `sprint-N-done`. После прохождения команды коммит — и, на границе спринта, тег — **пушатся на origin** (14.4, D-48). Единственное исключение из обязательности этой команды — аварийный коммит только md-состояния (14.4).
